# การออกแบบสถาปัตยกรรมเกมแบบ Modular ผ่านอุปมา “นาฬิกา”

> เอกสารสรุปโครงงาน — อธิบายว่าเรากำลังทำอะไร ทำไมถึงเลือกนาฬิกาเป็นแกน
> และวัดผลอย่างไรว่าโครงสร้างนี้ “modular จริง”
>
> โปรเจคปฏิบัติ: **EscapeRoom** — เกม escape room มุมมองบุคคลที่หนึ่ง
> Unity 6000.3.5f2 / URP / Input System 1.17

---

## 1. โจทย์ของงานวิจัย

โค้ดเกมส่วนใหญ่โตขึ้นตามแบบ **“หนึ่งสิ่งของ = หนึ่งคลาส”** นาฬิกาแขวนได้คลาสหนึ่ง
นาฬิกาตั้งพื้นได้อีกคลาสหนึ่ง นาฬิกาปลุกได้อีกคลาส แต่ละคลาสมีโค้ดหมุนเข็มของตัวเอง
พอมีนาฬิกา 8 แบบ ก็มีโค้ดหมุนเข็ม 8 ชุดที่ต้องแก้พร้อมกันทุกครั้ง

ผลที่ตามมามีสองอย่างและอย่างที่สองแพงกว่ามาก

1. **โค้ดซ้ำ** — แก้บั๊กหนึ่งจุดต้องไล่แก้แปดที่ ลืมที่เดียวคือบั๊กกลับมา
2. **คอขวดที่คน** — คนทำหน้าบ้าน (level designer, artist, คนวางฉาก) อยากได้
   “นาฬิกาแบบใหม่” หนึ่งเรือน ต้องรอโปรแกรมเมอร์เขียนคลาสใหม่ให้เสมอ

**คำถามวิจัยของโครงงานนี้คือข้อ 2:**
จะออกแบบระบบอย่างไร ให้การเพิ่มของใหม่เข้าเกม เป็นการ **ประกอบชิ้นส่วนที่มีอยู่แล้ว**
มากกว่าการเขียนคลาสใหม่ — และเมื่อจำเป็นต้องเขียนของใหม่จริง ๆ
ให้กระทบโค้ดเดิม **ศูนย์บรรทัด**

## 2. ทำไมต้อง “นาฬิกา”

เพราะนาฬิกาเป็นตัวอย่างที่ **อธิบายหลัก modular ได้ด้วยตัวมันเอง** โดยไม่ต้องใช้ศัพท์โปรแกรม

### 2.1 หน้าปัดคือ “การแสดงผลเวลา” — ไม่ใช่ “นาฬิกา”

ถ้าเราเอาหน้าปัดไปติดไว้กับอะไรก็ตาม — ผนัง กระเป๋าเสื้อ ข้อมือ หัวเตียง ตู้ไม้ —
**สิ่งนั้นกลายเป็นนาฬิกาทันที** เพราะหน้าที่ของนาฬิกาคือ *บอกเวลา*
และหน้าปัดคือสิ่งที่ทำหน้าที่นั้น

นี่คือประโยคที่กลายเป็น interface แรกของระบบ:

```csharp
public interface IClockDisplay
{
    void Show(float minutes);   // นาทีนับจาก 12 นาฬิกา
}
```

`ClockMovement` (กลไก) เก็บ “เวลา” ไว้เป็นตัวเลข แล้วยื่นให้ทุกอย่างที่แสดงผลได้
**มันไม่เคยถูกบอกว่า “การแสดงผล” หน้าตาเป็นอย่างไร**

### 2.2 “เดิน” หรือ “ไม่เดิน” เป็นคนละคำถามกับ “แสดงเวลา”

หน้าปัดที่ตอกติดผนังเฉย ๆ ก็ยังเป็นนาฬิกา — แค่นาฬิกาที่เข็มไม่เดิน
สิ่งที่ทำให้มัน *เดิน* คือชิ้นส่วนอื่นที่ติดมาด้วย: ลาน ลูกตุ้ม ตุ้มถ่วง ถ่านไฟฉาย

```csharp
public interface IClockPart
{
    bool Allows { get; }          // มีสิทธิ์ยับยั้ง — ชิ้นเดียวเสีย นาฬิกาหยุด
    float RateScale { get; }      // มีสิทธิ์ปรับอัตราเร็ว
    void Prime(bool foundRunning);
    void Draw(float minutes);     // ถูกดึงพลังงานทุกนาทีที่เข็มเดิน
}
```

`ClockMovement` ถาม **ทุกชิ้นส่วน** ก่อนขยับเข็มหนึ่งครั้ง ถ้าไม่มีชิ้นส่วนเลย
มันก็เดินตลอดกาล ซึ่ง **ถูกต้อง** — เพราะนาฬิกาที่ไม่มีอะไรให้หมดพลังงาน ก็ไม่มีวันหยุด

### 2.3 “ชนิด” ของนาฬิกา = ผลรวมของชิ้นส่วน

จุดสำคัญที่สุดของอุปมานี้:

> นาฬิกาตั้งพื้น ไม่ใช่ *ชนิด* ของนาฬิกา
> แต่คือ **หน้าปัด + กลไก + ลูกตุ้ม + ตุ้มถ่วง + ตู้ไม้สูงสองเมตร**
>
> นาฬิกากาเหว่า ไม่ใช่ *ชนิด* ของนาฬิกา
> แต่คือ **หน้าปัด + กลไก + ลาน + ลูกตุ้ม + ประตูที่เปิดตามชั่วโมง**

ในระบบเดิม สองอย่างนี้จะเป็น `LongcaseClock : Clock` และ `CuckooClock : Clock`
ในระบบนี้ **ไม่มีคลาสไหนชื่อทั้งสองอย่าง** มีแต่ prefab ที่ประกอบชิ้นส่วนต่างกัน

> **ผลที่ตามมาโดยตรง:** ในเกมนี้มีนาฬิกา 47 เรือน 8 แบบ
> ทั้ง 47 เรือนใช้ `ClockDial` prefab **ตัวเดียวกัน** และไม่มีคลาสใดชื่อ `WallClock`,
> `PocketWatch` หรือ `AlarmClock` เลยแม้แต่คลาสเดียว

## 3. สถาปัตยกรรม: ตั้งชื่อตาม “บทบาท” ไม่ใช่ “กลไก”

ทั้งระบบสร้างจาก interface 9 ตัว แต่ละตัวคือ *รอยต่อ (seam)* ที่คนอื่นเสียบของใหม่เข้ามาได้

| Interface | บทบาท | มีกี่ implementation | ตัวอย่าง |
|---|---|---|---|
| `IClockDisplay` | อะไรก็ได้ที่แสดงเวลาได้ | 2 (+1 ในเทสต์) | `ClockDial`, `DigitalReadout` |
| `IClockPart` | อะไรก็ได้ที่มีสิทธิ์ยับยั้ง/ปรับอัตราเร็ว | 2 | `Mainspring`, `Pendulum` |
| `IPowerStore` | ที่เก็บพลังงานของนาฬิกา | 1 | `Mainspring` |
| `IInteractable` | อะไรก็ได้ที่กด **E** ใส่ได้ | 7 | `ClockWinder`, `WeightChain`, `Openable`, `CodeWheel`, … |
| `IInspectable` | อะไรก็ได้ที่กด **F** ดูใกล้ ๆ ได้ | 1 | `Inspectable` |
| `IItemReceiver` | อะไรก็ได้ที่รับของจากกระเป๋าได้ | 2 | `KeyLock`, `ClockPartSocket` |
| `ILock` | อะไรก็ได้ที่ล็อกประตูไว้ได้ | 6 | `KeyLock`, `CodeLock`, `TimeLock`, `RunningLock`, `StarLock`, `SealedLock` |
| `ICodeInput` | อะไรก็ได้ที่ผู้เล่นใส่ตัวเลขได้ | 1 | `CodeWheel` |
| `IActor` | ใครก็ได้ที่กำลังใช้งานของชิ้นนั้นอยู่ | 1 (+1 ในเทสต์) | `PlayerInteractor` |

สองแถวที่เขียนว่า "+1 ในเทสต์" คือ implementation ที่อยู่ในชุดทดสอบ ไม่ใช่ในเกม —
และมันคือหลักฐานที่ดีที่สุดว่ารอยต่อสองอันนี้เปิดจริง เพราะคลาสที่เสียบเข้ามา
ถูกเขียนขึ้น *หลัง* และ *นอก* โมดูลที่ประกาศ interface ไว้

### กฎการตั้งชื่อที่ใช้จริง

interface ถูกตั้งชื่อตาม **บทบาท** ไม่ใช่ตาม implementation แรกที่บังเอิญเขียนก่อน

ตัวอย่างที่ชัดที่สุดคือ `IPowerStore` ตอนแรกมันเกือบชื่อ `IMainspring` (ลาน)
ซึ่งจะแปลว่า *สปริงตัวหนึ่งที่ใส่เสื้อ interface* — ตุ้มถ่วงหรือถ่านไฟฉายจะกลายเป็น
พลเมืองชั้นสอง พอเปลี่ยนเป็น `IPowerStore` (ที่เก็บพลังงาน) ทั้งสามอย่างเท่าเทียมกัน
และ method ก็เปลี่ยนจาก `Wind()` (ไขลาน) เป็น `Fill()` (เติม) ตามไปด้วย

**ข้อสรุปเชิงวิธีการ:** ถ้า interface ถูกตั้งชื่อตามกลไกใดกลไกหนึ่ง
มันจะกลายเป็น abstraction ที่รับได้แค่กลไกนั้น

## 4. หลักฐาน — ห้ากรณีศึกษาที่เกิดขึ้นจริงระหว่างพัฒนา

ทั้งห้ากรณีนี้ **ไม่ได้ออกแบบมาเป็นตัวอย่าง** แต่เป็นความต้องการที่เกิดขึ้นจริง
ระหว่างทำเกม แล้วบังเอิญกลายเป็นการทดสอบสถาปัตยกรรมไปในตัว

### กรณีที่ 1 — เพิ่มจอแสดงผลชนิดใหม่ (แก้โค้ดเดิม 0 บรรทัด)

ต้องการ: เครื่องจับเวลาดิจิทัลบนโต๊ะช่าง ที่แสดง “เวลาเดียวกัน” กับหน้าปัดเข็ม

สิ่งที่ทำ: เขียน `DigitalReadout.cs` ไฟล์เดียว (74 บรรทัด) implement `IClockDisplay`
แล้วเอาไปเป็นลูกของ `ClockMovement` ตัวเดิม

สิ่งที่ **ไม่ต้อง** ทำ:
- ไม่แก้ `ClockMovement` แม้แต่บรรทัดเดียว
- ไม่แก้ `ClockDial` แม้แต่บรรทัดเดียว
- ทั้งสองไม่รู้ด้วยซ้ำว่าอีกฝ่ายมีตัวตน

ผลลัพธ์: กลไกเดียวกัน ขับจอสองแบบพร้อมกัน ทั้งคู่แสดง 4:40 ตรงกัน
เพราะทั้งคู่ได้รับ *ตัวเลขเดียวกัน* — นี่คือข้ออ้างทั้งหมดของสถาปัตยกรรม
วางอยู่บนโต๊ะให้ดูได้

### กรณีที่ 2 — เปลี่ยนวิธีให้พลังงาน โดยที่ตัวรับผลไม่รู้เรื่อง

ต้องการ: นาฬิกากาเหว่าไม่ควรมีที่ไขลาน — ควร **ดึงโซ่ตุ้มถ่วง** แทน
แล้วนกยังต้องออกมาร้องตามจำนวนชั่วโมงเหมือนเดิม

ก่อนแก้: `ClockStriker` (ตัวสั่งให้นกออก) ฟัง event จาก `ClockWinder` (ที่ไขลาน) โดยตรง
→ ถ้าเอาที่ไขลานออก นกก็ตาย

สิ่งที่ทำ: **ย้าย event ขึ้นไปอยู่ที่ “ที่เก็บพลังงาน” แทนที่จะอยู่ที่ “ที่ไขลาน”**

```csharp
// เดิม  — striker ผูกกับกลไกเฉพาะอย่าง
winder.Wound += Strike;

// ใหม่  — striker ผูกกับ "พลังงานถูกเติม" เฉย ๆ
_power.Filled += Strike;
```

ผลลัพธ์: เขียน `WeightChain.cs` ใหม่ไฟล์เดียว (โซ่ที่ดึงได้)
`ClockStriker` **ไม่ต้องรู้เลย** ว่าคราวนี้พลังงานมาจากมือที่ดึงโซ่ ไม่ใช่มือที่หมุนลาน
และเพราะตุ้มถ่วงลอยสูงตาม `_power.Charge` ตัวที่ให้พลังงานจึงกลายเป็น
**มาตรวัดพลังงานที่เหลือไปในตัว** โดยไม่ต้องเขียนโค้ดเพิ่ม

### กรณีที่ 3 — ปริศนาที่ “เล่น” ตัวสถาปัตยกรรมเอง

ปริศนาองก์ที่ 4: นาฬิกาตั้งพื้นในห้องนอนถูกตั้งค่าไว้ว่า `Running` แต่ยืนนิ่งสนิท
เพราะ `Pendulum` และ `Mainspring` ของมัน **ถูกปิดไว้** ผู้เล่นต้องหาลูกตุ้มกับตุ้มถ่วง
มาใส่ทีละชิ้น

- ใส่ลูกตุ้มอย่างเดียว → ยังไม่เดิน (ไม่มีพลังงาน)
- ใส่ตุ้มถ่วงอย่างเดียว → ยังไม่เดิน (ไม่มีตัวคุมจังหวะ)
- ใส่ครบสองชิ้น → เดิน → `ChimeRelease` บนผนังได้ยินว่ามันเริ่มเดิน → ตีระฆัง 5 วินาที → ทางลับเปิดเอง

**ไม่มีโค้ดปริศนาแม้แต่บรรทัดเดียวที่เขียนขึ้นเพื่อเรื่องนี้**
มันคือกฎ “ทุกชิ้นส่วนมีสิทธิ์ยับยั้ง” ที่มีอยู่แล้ว ถูกนำมาใช้เป็นกลไกเกมตรง ๆ
`ClockPartSocket` แค่เปิดสวิตช์ component และ `ChimeRelease` แค่อ่าน `movement.IsRunning`
ส่วนผนังไม่เคยถูกบอกว่านาฬิกาคืออะไร มันมีแค่ `Openable` กับ `SealedLock` —
และ `SetOpen` ที่ขยับของโดยไม่สนใจล็อก ซึ่งเป็นวิธีเดียวกับที่ล็อกทุกตัวปลดสลักตัวเอง

> นี่คือประโยชน์ที่วัดยากที่สุดแต่สำคัญที่สุดของ modular design:
> **ระบบที่ประกอบกันได้ ให้ gameplay ที่ไม่ได้ถูกออกแบบมาก่อนเป็นของแถม**

### กรณีที่ 4 — ทำให้ข้ออ้างกลายเป็น compile error

สามกรณีข้างบนพิสูจน์ว่าสถาปัตยกรรม *ทำงาน* แต่ยังไม่ได้พิสูจน์ว่ามัน *ถูกบังคับ*
ตอนนั้นทั้งโปรเจคอยู่ใน assembly เดียว ใครจะเขียน `GetComponent<PlayerMovement>()`
ลงใน `ClockDial` ก็ยังคอมไพล์ผ่าน

ต้นเหตุคือพารามิเตอร์ตัวเดียว — `Interact(PlayerInteractor)` — ทำให้ของทุกชิ้นในเกม
ถูกคอมไพล์ติดกับคลาสผู้เล่น ทั้งที่ใช้ความสามารถของมันแค่สามอย่าง

สิ่งที่ทำ: `IActor` (3 เมธอด) แทนที่ `PlayerInteractor` ในลายเซ็นทั้งหมด — แตะ 13 ไฟล์
ส่วนใหญ่แก้บรรทัดเดียว — แล้ววาง `.asmdef` ห้าไฟล์บนชั้นล่างของบ้าน

**ผลที่อ่านออกมาจาก DLL ที่ Unity คอมไพล์เอง:**

```
EscapeRoom.Items        →  (ไม่อ้างใคร)
EscapeRoom.Interaction  →  Items
EscapeRoom.Clock        →  Items, Interaction
EscapeRoom.Puzzle       →  Interaction
EscapeRoom.World        →  (ไม่อ้างใคร)

Assembly-CSharp (Player · UI · Game)  →  อ้าง EscapeRoom.* ได้   ← ทางเดียว
```

ไม่มี DLL ไหนในห้าตัวนี้มีคำว่า `Assembly-CSharp` อยู่เลย
**`Clock` แตะ `Player` ไม่ได้แล้ว ไม่ใช่เพราะเราตั้งใจ แต่เพราะคอมไพเลอร์ไม่ยอม**

และเพราะ prop รับ `IActor` แทนตัวผู้เล่น เราจึงเขียนชุดทดสอบที่ **ไม่ต้องเปิดฉาก
ไม่ต้องมีผู้เล่น** ได้ — คลาส C# ธรรมดา 12 บรรทัดที่ implement `IActor`
เปิดตู้ ไขกุญแจ และใส่ชิ้นส่วนนาฬิกาได้ทั้งหมด สิบเทสต์ ผ่านครบ

> นี่คือความต่างระหว่าง *“ผมพยายามไม่ให้มันพึ่งกัน”* กับ *“มันพึ่งกันไม่ได้”*
> สำหรับงานวิจัย ความต่างตรงนี้คือทุกอย่าง

### กรณีที่ 5 — ทำให้ข้ออ้างเขียนออกมาเป็นข้อมูลได้

จุดที่โปรเจคขัดกับตัวเองมานาน: เราบอกว่า *ชนิดของนาฬิกาคือผลรวมของชิ้นส่วน*
แต่เครื่องมือของเราไม่ยอมให้เขียน "ผลรวม" นั้นออกมาเป็นข้อมูล — นาฬิกาแบบใหม่
ยังต้องเป็นเมธอด C# ยาว 90 บรรทัด

สิ่งที่ทำ: `ClockRecipe` — ScriptableObject ที่มีแค่ *ตู้หนึ่งใบ* กับ *รายการของที่บอลต์ติดไว้*

จุดที่สำคัญที่สุดของมันคือสิ่งที่มัน **ไม่มี**: ไม่มีช่อง "จอ" แยกจากช่อง "ชิ้นส่วน"
ทั้งสองอย่างเป็นแค่ *ของที่เอาไปบอลต์* เหมือนกัน แล้ว `ClockMovement` ไปแยกเองว่าอันไหน
เป็นอะไร ด้วยการถามว่ามัน implement interface อะไร — นั่นคือวิทยานิพนธ์ทั้งอัน
นั่งอยู่ใน Inspector ให้ดีไซเนอร์แก้ได้

**ผลลัพธ์:** `PlankClock` — ไม้กระดานแผ่นหนึ่งที่กลายเป็นนาฬิกาเพราะมีหน้าปัดติดอยู่
ไม่มีเมธอด C# ตัวไหนสร้างมัน มีแค่ไฟล์ข้อมูลหนึ่งไฟล์ และมันเดินจริง หยุดจริง
ถอดลูกตุ้มแล้วหยุดจริง เหมือนนาฬิกาอีกแปดแบบที่เขียนด้วยโค้ดทุกประการ

> **นี่คือคำตอบตรง ๆ ของคำถามวิจัย** — "นาฬิกาแบบใหม่" เข้าระบบทางไฟล์ข้อมูล
> ไม่ใช่ทางเมธอดใหม่ คนหน้าบ้านทำเองได้ โดยไม่ต้องรอโปรแกรมเมอร์

## 5. กฎที่บังคับใช้จริงในโปรเจค


| กฎ | เหตุผล |
|---|---|
| **ไม่มี inheritance เลย** — ทุกคลาสสืบจาก `MonoBehaviour` ตรง ๆ | ลำดับชั้นคือการตัดสินใจล่วงหน้าว่า “อะไรเป็นชนิดของอะไร” ซึ่งจะผิดเสมอเมื่อของใหม่มาถึง |
| **ไม่มี abstract class เลย** | เหตุผลเดียวกัน |
| **ขอบเขตโมดูลเป็น compile error ไม่ใช่ข้อตกลง** | `.asmdef` ห้าไฟล์บนชั้นล่างของบ้าน — asmdef อ้าง `Assembly-CSharp` ไม่ได้ ชั้นล่างจึงแตะชั้นบนไม่ได้เลย |
| **ไม่มี `GameObject.Find` ใน runtime** | การหาของด้วยชื่อคือการผูกกับโครงสร้างฉาก ซึ่งคนทำหน้าบ้านจะเปลี่ยนแน่นอน |
| **หนึ่งคลาส หนึ่งหน้าที่** | ค่าเฉลี่ย 59 บรรทัด/ไฟล์ อ่านจบได้ในหน้าจอเดียว |
| **ค้นหา (discover) แทนต่อสาย (wire) เมื่อทำได้** | `ClockMovement` หา display และ part เอง, `ClockStriker` หา power store เอง — ติดชิ้นส่วนเพิ่มแล้วทำงานทันที ไม่ต้องลาก reference ใน Inspector |
| **enum สำหรับ “ตัวแปรของสิ่งเดียวกัน”, component ใหม่สำหรับ “ความสามารถใหม่”** | `ClockCondition` (Running/Slow/Reversed/Stopped/Broken) คือ *อาการ* ของนาฬิกาเรือนหนึ่ง ไม่ใช่ความสามารถใหม่ จึงเป็น enum ไม่ใช่ 5 คลาส |
| **ฉากถูกสร้างจากข้อมูลด้วย editor script** | `HouseBuilder`, `ClockBuilder`, `DressingBuilder`, `TextureKit` — ย้ายห้องคือแก้ตัวเลขสองตัว ไม่ใช่ลากกล่องสามสิบใบ |
| **ข้อมูลที่ดีไซเนอร์แก้อยู่ในไฟล์ ไม่ใช่ในซอร์ส** | `HousePlan.asset` (ผังบ้าน) และ `ClockRecipe` (ชนิดนาฬิกา) — สองอย่างที่คนหน้าบ้านต้องแก้บ่อยที่สุด ย้ายออกจาก C# แล้ว |

## 7. ประโยชน์ต่อคนทำหน้าบ้าน

นี่คือเหตุผลที่ทำโครงงานนี้ตั้งแต่แรก

| คนหน้าบ้านอยากได้ | ต้องทำอะไร | ต้องรอโปรแกรมเมอร์ไหม |
|---|---|---|
| นาฬิกาแบบใหม่ที่ไม่มีในเกม | ประกอบ prefab จากชิ้นส่วนที่มี | **ไม่** |
| นาฬิกาเรือนนี้ให้เดินช้า | เปลี่ยน `ClockCondition` เป็น `Slow` | **ไม่** |
| นาฬิกาเรือนนี้พังถาวร | เอา `Mainspring` ออก / ตั้งเป็น `Broken` | **ไม่** |
| ตู้ที่ต้องใช้ทั้งกุญแจและรหัส | ใส่ `KeyLock` + `CodeLock` ทั้งคู่ | **ไม่** |
| ประตูที่เลื่อนขึ้นแทนที่จะบานเปิด | เปลี่ยน `SwingMotion` เป็น `SlideMotion` ชี้ขึ้น | **ไม่** |
| ตู้โชว์ที่ปลดล็อกเมื่อนาฬิกาเดิน | ใส่ `RunningLock` | **ไม่** |
| จอแสดงเวลาแบบใหม่ (เข็มวินาที, ตัวเลข, เสียง) | เขียนคลาสใหม่ implement `IClockDisplay` | **ใช่ แต่แก้ของเดิม 0 บรรทัด** |

แถวสุดท้ายคือหัวใจ: ยังต้องมีโปรแกรมเมอร์อยู่ แต่**งานของโปรแกรมเมอร์กลายเป็น
“เพิ่มของใหม่” แทนที่จะเป็น “ไปแก้ของเก่าให้รองรับของใหม่”** ซึ่งเป็นงานที่
ไม่ทำให้เกิด regression และรีวิวได้ง่ายกว่ามาก

## 8. ข้อจำกัดและงานต่อไป

เอกสารนี้พยายามไม่ขายเกินจริง สิ่งที่ยังเป็นจุดอ่อน:

1. **`IPowerStore` ยังมี implementation เดียว** (`Mainspring`) รอยต่อถูกเปิดไว้แล้ว
   และพิสูจน์แล้วว่าใช้งานได้ (กรณีศึกษาที่ 2) แต่ยังไม่มีคลาสที่สองมายืนยัน
   เช่นเดียวกับ `ICodeInput` และ `IInspectable`
2. **`InspectView` ยาว 315 บรรทัด** และตัดสินใจจาก `InspectStyle` enum 3 ค่า
   ตรงนี้เป็นการตัดสินใจโดยเจตนา (สามแบบคือ “วิธีมอง” ไม่ใช่ “ความสามารถ”)
   แต่ถ้ามีแบบที่สี่และห้า ควรแยกเป็น strategy component
3. **การค้นหาชิ้นส่วนใช้ลำดับชั้นของ GameObject** — นาฬิกาที่มีที่เก็บพลังงานสองอัน
   จะเจออันแรกเท่านั้น ข้อจำกัดนี้ถูกบันทึกไว้ในโค้ดแล้ว
4. **ข้อความในเกมยังฝังอยู่ในคอมโพเนนต์** — 17 จุด ไม่มีช่องทางแปลภาษา
   และนาฬิกาสองเรือนแบบเดียวกันต้องเก็บประโยคเดียวกันคนละชุด เป็นชิ้นถัดไปที่ควรทำ
5. **`Player` กับ `UI` ยังไม่ได้แยก assembly** — สองกล่องนี้พึ่งกันไปมาจริง
   และ assembly เป็นวงไม่ได้ ทางแก้คือรวมเป็นกล่องเดียว ซึ่งต้องย้าย `PlayerControls.cs`
   ออกจาก `Assets/` ก่อน ยังไม่ได้ทำเพราะเสี่ยงกับ generated-path ของ Input System
   และไม่กระทบข้ออ้างหลัก (ชั้นล่างถูกบังคับแล้ว)
6. **ยังไม่มีการวัดเชิงปริมาณกับผู้ใช้จริง** — ตัวเลขทั้งหมดในเอกสารนี้เป็น
   metric ของโค้ด ยังไม่ได้ทดลองให้คนที่ไม่ใช่ผู้เขียนลองต่อของใหม่แล้วจับเวลา
   ซึ่งเป็นขั้นตอนที่ควรทำต่อ
