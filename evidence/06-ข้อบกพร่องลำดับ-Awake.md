# หลักฐาน 06 — ข้อบกพร่อง `NullReferenceException` ที่ `DigitalReadout.cs:67`

เก็บเมื่อ **8 พฤศจิกายน 2569** จากการอ่านซอร์สโค้ดและไฟล์ตั้งค่าของโปรเจกต์
**ไม่ได้กด Play** ตามข้อกำหนด read-only

ไฟล์นี้ตอบช่องว่าง **ข้อ 2 ของบทที่ 4** และ **ข้อ 2 ของบทที่ 5** —
*"ยืนยันว่า `NullReferenceException` เกิดทุกครั้งหรือไม่"*

**คำตอบ: วิเคราะห์จากโค้ดได้แล้วว่าข้อบกพร่องนี้ "ไม่แน่นอนโดยการออกแบบ"
และไม่สามารถยืนยันว่าเกิดทุกครั้งได้จากโค้ดเพียงอย่างเดียว — แต่เงื่อนไขที่ทำให้เกิด
ถูกยืนยันครบทุกข้อแล้ว** รายละเอียดด้านล่าง

---

## 1. สายการเกิดเหตุ ยืนยันครบทุกขั้นจากโค้ดจริง

```
ClockMovement.Awake()                           ClockMovement.cs:107
  └─ _displays = GetComponentsInChildren<IClockDisplay>(true)   :112
  └─ ShowTime()                                                 :128   ◄── เรียกใน Awake
       └─ foreach display → display.Show(_minutes)               :157-158
            └─ DigitalReadout.Show(minutes)        DigitalReadout.cs:44
                 └─ SetDigit(0, ...)                             :53
                      └─ if (_showing[place] == value) return;   :63   ◄── ไม่ดักได้ (ดูข้อ 3)
                      └─ _faces[place].SetTextureOffset(...)     :67   ◄── NullReferenceException
```

`_faces` ถูกกำหนดค่าที่ `DigitalReadout.Awake()` บรรทัด **36–42** เท่านั้น

```csharp
private void Awake()
{
    _faces = new Material[digits.Length];
    for (int i = 0; i < digits.Length; i++)
        _faces[i] = digits[i].material;
}
```

**ดังนั้นเงื่อนไขของข้อบกพร่องคือ: `ClockMovement.Awake` ทำงานก่อน `DigitalReadout.Awake`**

## 2. ทำไมลำดับนี้จึงไม่แน่นอน — ยืนยันสามข้อ

### 2.1 สองคอมโพเนนต์อยู่บน GameObject ต่างใบ (ยืนยันแล้ว)

`DressingBuilder.cs:728-766` ฟังก์ชัน `FitTimingMachine(Transform movement)`

```csharp
Transform box = Group("TimingMachine", movement, new Vector3(0.47f, -0.21f, 0.02f));
...
var readout = box.gameObject.AddComponent<DigitalReadout>();
```

`TimingMachine` เป็น **ลูก** ของ GameObject ที่มี `ClockMovement`
และ `DigitalReadout` อยู่บนลูกใบนั้น ไม่ใช่บนใบเดียวกับกลไก

คอมเมนต์ในโค้ดบรรทัด 725–727 ระบุเจตนานี้ไว้ชัดว่า
*"It is a child of the movement because that is what 'plugged into' means here"*

### 2.2 Unity ไม่รับประกันลำดับ `Awake` ระหว่าง GameObject ต่างใบ

เป็นพฤติกรรมที่เอกสาร Unity ระบุไว้เอง: ลำดับการเรียก `Awake` ระหว่างอ็อบเจกต์
หลายใบไม่มีการรับประกัน เว้นแต่จะตั้ง Script Execution Order

### 2.3 โปรเจกต์นี้ไม่ได้ตั้ง Script Execution Order เลย — **ยืนยันด้วยการไม่มีไฟล์**

Unity เก็บค่า Script Execution Order ไว้ในไฟล์ `ProjectSettings/MonoManager.asset`

```
$ ls ProjectSettings/MonoManager.asset
ls: cannot access 'MonoManager.asset': No such file or directory
```

**ไฟล์นี้ไม่มีอยู่ในโปรเจกต์** รายการไฟล์ทั้งหมดใน `ProjectSettings/` มี 24 ไฟล์
และไม่มี `MonoManager.asset` อยู่ในนั้น

> นี่เป็นหลักฐานที่แข็งกว่า "ค้นแล้วไม่พบ" เพราะการไม่มีไฟล์นี้เลยหมายความว่า
> **ไม่เคยมีการตั้งค่าลำดับการทำงานของสคริปต์ในโปรเจกต์นี้แม้แต่ครั้งเดียว**
> (ถ้าตั้งแล้วลบออก Unity จะยังเก็บไฟล์เปล่าไว้)

## 3. ทำไมตัวดักที่บรรทัด 63 ดักไม่ได้

```csharp
private const int Unset = -2;
private readonly int[] _showing = { Unset, Unset, Unset, Unset };   // :34
...
if (_showing[place] == value) return;                                // :63
```

`_showing` ถูกกำหนดค่าที่ระดับ field (ไม่ใช่ใน `Awake`) จึงมีค่า `-2` อยู่แล้วเสมอ
ตั้งแต่ก่อน `Awake` ของตัวมันเอง และค่า `value` ที่ส่งเข้ามาจาก `Show` คือ
0–9 หรือ `-1` **ไม่มีทางเป็น `-2`** ดังนั้นการเรียกครั้งแรกจะผ่านตัวดักไปถึงบรรทัด 67 แน่นอน

และคอมเมนต์บรรทัด 19–21 ระบุเองว่าตั้ง `Unset` เป็น `-2` แทน `Blank` (`-1`) **โดยเจตนา**
เพื่อให้การเรียกครั้งแรกไม่เป็น no-op — ซึ่งเป็นการตัดสินใจที่ถูกสำหรับภาพที่เห็นบนจอ
แต่เป็นสิ่งที่ทำให้ข้อบกพร่องนี้เกิดขึ้นได้ทุกครั้งที่ลำดับผิด

## 4. ทำไมมีแค่ `DigitalReadout` ที่พัง — คำตอบที่น่าสนใจที่สุดของเรื่องนี้

`IClockDisplay` มีสองการสร้างจริงในโปรเจกต์ (`ClockDial` และ `DigitalReadout`)
และนาฬิกา 46 เรือนในฉากใช้ `ClockDial` ทั้งหมด แต่ไม่มีเรือนใดพัง

เพราะ **`ClockDial` ไม่มี `Awake` เลย**

| | `ClockDial` | `DigitalReadout` |
|---|---|---|
| มี `Awake` | **ไม่มี** | มี (`:36`) |
| สิ่งที่ `Show` ต้องใช้ | `hourHand`, `minuteHand`, `secondHand` | `_faces`, `digits` |
| สิ่งนั้นมาจากไหน | **`[SerializeField]`** | `_faces` สร้างใน `Awake` |
| พร้อมใช้เมื่อไร | ตั้งแต่ Unity deserialize ก่อน `Awake` ทุกตัวจะทำงาน | หลัง `Awake` ของตัวเองเท่านั้น |
| ทนต่อ `Show` ก่อน `Awake` | **ทนได้** | **ไม่ทน** |

> **กฎที่ได้จากเรื่องนี้ และเขียนลงบทที่ 5 ได้เลย**
> `ClockMovement` เรียก `Show` จาก `Awake` ของตัวเอง ซึ่งเป็นสัญญาที่ไม่ได้เขียนไว้ว่า
> *"ผู้รับต้องพร้อมใช้งานก่อน `Awake` ของตัวเอง"* — `ClockDial` ทำตามสัญญานี้โดยบังเอิญ
> เพราะมันใช้แต่ `[SerializeField]` ส่วน `DigitalReadout` ละเมิดสัญญาโดยไม่มีใครรู้
> เพราะสัญญาข้อนี้ไม่มีที่ไหนเขียนไว้
>
> นี่คือ **จุดอ่อนของการค้นหาผู้ร่วมงานด้วยอินเทอร์เฟซ (discovery by interface)**
> ซึ่งเป็นหัวใจของสถาปัตยกรรมโครงงานนี้: อินเทอร์เฟซบังคับได้แค่ *ลายเซ็นของเมธอด*
> บังคับ *ช่วงเวลาที่เรียกได้* ไม่ได้ และนั่นคือสิ่งที่พลาดไปตรงนี้พอดี

## 5. ความถี่ของการเกิด — สรุปอย่างตรงไปตรงมา

| คำถาม | คำตอบที่หลักฐานรองรับ |
|---|---|
| เงื่อนไขที่ทำให้เกิด มีอยู่จริงหรือไม่ | **มีจริง ยืนยันครบทุกข้อ** (ข้อ 1–3 ข้างบน) |
| เกิดทุกครั้งที่กด Play หรือไม่ | **ยืนยันจากโค้ดไม่ได้** เพราะขึ้นกับลำดับที่ Unity เลือกเอง ซึ่งไม่มีการรับประกัน |
| ในทางปฏิบัติ Unity มักเรียงลำดับแบบใด | ในทางปฏิบัติ Unity มักเรียก `Awake` ตามลำดับที่อ็อบเจกต์ถูกเก็บในฉาก ซึ่ง**มักจะ**ทำให้พ่อทำงานก่อนลูก — ถ้าจริงในเครื่องนี้ ข้อบกพร่องจะเกิดทุกครั้ง · **ข้อนี้เป็นการคาดการณ์ ไม่ใช่หลักฐาน** |
| Console ตอนนี้มีข้อผิดพลาดไหม | **ไม่มี** — อ่านผ่าน MCP เมื่อ 8 พ.ย. 2569 ได้ 0 รายการ แต่ Console อาจถูกเคลียร์หรือ Editor เพิ่งเปิดใหม่ **จึงไม่เป็นหลักฐานว่าไม่เกิด** |
| ชุดทดสอบจับได้ไหม | **ไม่ได้** — ไม่มีกรณีทดสอบใดใน 15 กรณีที่สร้าง `DigitalReadout` ขึ้นมา (ดู `04-ชุดทดสอบ-15-กรณี.md` ข้อ 3) |
| ผลกระทบต่อผู้เล่น | **จำกัดมาก** — มี `DigitalReadout` เพียง 1 ตัวในฉากทั้งฉาก (ตรวจด้วย `find_gameobjects by_component` ได้ instanceID 50186 หนึ่งรายการ) อยู่บนเครื่องจับเวลาบนโต๊ะช่างซึ่งเป็นของประกอบฉาก ไม่ใช่ส่วนของปริศนาใด · ข้อยกเว้นเกิดใน `Awake` ครั้งเดียว ไม่ได้เกิดทุกเฟรม และจอจะเริ่มแสดงเวลาถูกต้องตั้งแต่ `Update` เฟรมถัดไป |

### สิ่งที่ยังต้องรันเองเพื่อปิดข้อนี้ให้สนิท

เคลียร์ Console แล้วกด Play หนึ่งครั้ง จดสองอย่าง
1. มี `NullReferenceException` ที่ `DigitalReadout.Show` หรือไม่
2. ถ้ามี ให้กด Stop แล้ว Play ซ้ำอีก 2–3 ครั้ง เพื่อดูว่าเกิดทุกครั้งหรือเกิดบางครั้ง

**ผลที่ได้จะเปลี่ยนคำในรายงานแค่คำเดียว** — "เกิดทุกครั้ง" หรือ "เกิดเป็นบางครั้ง"
ส่วนการวิเคราะห์สาเหตุทั้งหมดข้างบนไม่เปลี่ยน

## 6. วิธีแก้ที่ถูกต้องที่สุด (สำหรับข้อเสนอแนะในบทที่ 5)

เรียงจากตรงจุดที่สุดไปน้อยที่สุด

| วิธี | แก้อะไร | ความเห็น |
|---|---|---|
| **ย้ายการสร้าง `_faces` ออกจาก `Awake` ไปเป็น lazy ใน `SetDigit`** | ผู้รับพร้อมใช้งานตลอดเวลา ไม่ขึ้นกับลำดับ | **ตรงจุดที่สุด** เพราะแก้ที่ต้นเหตุคือ "ผู้รับยังไม่พร้อม" โดยไม่แตะใครอื่น |
| ให้ `ClockMovement` เรียก `ShowTime()` ใน `Start` แทน `Awake` | `Start` ทุกตัวทำงานหลัง `Awake` ทุกตัวเสมอ | ถูกต้องและสะอาด แต่เปลี่ยนพฤติกรรม: เข็มจะไม่อยู่ที่เวลาเริ่มต้นในเฟรมแรกสุด |
| ตั้ง Script Execution Order ให้ `DigitalReadout` มาก่อน `ClockMovement` | บังคับลำดับ | ได้ผล แต่เป็นการตั้งค่าที่มองไม่เห็นจากโค้ด และต้องจำทุกครั้งที่เพิ่มจอชนิดใหม่ — ขัดกับหลัก "เสียบแล้วใช้ได้เลย" ของโครงงาน |
| ใส่ `if (_faces == null) return;` ที่ `SetDigit` | ซ่อนอาการ | **ขัดกับกฎในคู่มือโครงงานเองว่า "ห้ามกลบความผิดพลาดด้วย early return"** |

> ข้อเสนอแนะที่ควรเขียนในบทที่ 5 ไม่ใช่แค่ "ควรตั้ง Script Execution Order"
> แต่เป็นหลักการว่า **คอมโพเนนต์ที่ถูกค้นหาและเรียกใช้ผ่านอินเทอร์เฟซ
> ต้องพร้อมใช้งานตั้งแต่ก่อน `Awake` ของตัวเอง หรือผู้เรียกต้องเลื่อนไปเรียกใน `Start`**
> ซึ่งเป็นสิ่งที่โครงงานนี้แก้ถูกแล้วครั้งหนึ่งที่ `TestRun` ด้วยการย้ายไปใช้ `LateUpdate`
