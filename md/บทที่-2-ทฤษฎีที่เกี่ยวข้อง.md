## 2.1 ทฤษฎีการออกแบบซอฟต์แวร์เชิงโมดูล

### 2.1.1 การแยกระบบออกเป็นโมดูลและการซ่อนข้อมูล

การแยกระบบออกเป็นโมดูล (Modular Decomposition) คือการแบ่งซอฟต์แวร์ขนาดใหญ่ออกเป็นหน่วยย่อยที่พัฒนา ทดสอบ และแก้ไขได้โดยอิสระจากกัน Parnas เสนอไว้ว่าเกณฑ์ที่ควรใช้ในการแบ่งโมดูลไม่ใช่การแบ่งตามลำดับขั้นตอนการทำงานของโปรแกรม แต่ควรแบ่งตาม **สิ่งที่แต่ละโมดูลต้องปิดซ่อนไว้ไม่ให้โมดูลอื่นรู้** (Information Hiding) เพราะการเปลี่ยนแปลงในอนาคตมักเกิดขึ้นกับรายละเอียดภายใน ถ้ารายละเอียดนั้นถูกซ่อนไว้ การเปลี่ยนแปลงก็จะไม่ลุกลามออกไปนอกโมดูล [1]

ในโครงงานนี้ ซอร์สโค้ดถูกแบ่งออกเป็นโฟลเดอร์ตาม **โดเมนของระบบ** ไม่ใช่ตามชนิดของอ็อบเจกต์ในเอนจิน รวม 9 กลุ่ม ดังตารางที่ 2.1

ตารางที่ 2.1 โมดูลของโครงงาน จำนวนไฟล์ และขอบเขตระดับการคอมไพล์

ข้อสังเกตที่ควรบันทึก คือโครงงานนี้ **ไม่ใช้ `namespace` เลยแม้แต่ที่เดียว** ทุกคลาสอยู่ใน global namespace และทุกไฟล์ `.asmdef` ตั้งค่า `"rootNamespace": ""` การแบ่งโมดูลที่นี่จึงใช้ `.asmdef` เป็นเครื่องมือแทน namespace ซึ่งเข้มงวดกว่า เพราะ namespace เพียงจัดกลุ่มชื่อและข้ามได้ด้วยคำสั่ง `using` ขณะที่ `.asmdef` ปิดกั้นการอ้างถึงในระดับการคอมไพล์ ต้นทุนที่ตามมาคือหากนำแอสเซ็ตจากภายนอกที่มีคลาสชื่อซ้ำเข้ามา โปรเจกต์จะคอมไพล์ไม่ผ่านทันที

### 2.1.2 การเกาะเกี่ยว (Coupling) และการเกาะกลุ่ม (Cohesion)

Coupling และ Cohesion เป็นตัวชี้วัดคุณภาพของการแบ่งโมดูลที่ Stevens, Myers และ Constantine เสนอไว้ตั้งแต่ปี ค.ศ. 1974 [2] โดย

- **Coupling** คือระดับความขึ้นต่อกันระหว่างโมดูล ยิ่งต่ำยิ่งดี เพราะโมดูลที่ขึ้นต่อกันน้อยสามารถแก้ไขหรือแทนที่ได้โดยไม่กระทบโมดูลอื่น
- **Cohesion** คือระดับความเกี่ยวเนื่องกันของหน้าที่ภายในโมดูลเดียว ยิ่งสูงยิ่งดี เพราะโมดูลที่ทำหน้าที่เดียวย่อมเข้าใจและทดสอบได้ง่ายกว่าโมดูลที่ทำหลายหน้าที่ปนกัน

เป้าหมายของการออกแบบจึงมักสรุปสั้น ๆ ว่า **Low Coupling, High Cohesion** และในมาตรฐาน ISO/IEC 25010 ความสามารถเช่นนี้จัดอยู่ในคุณลักษณะคุณภาพด้าน Maintainability โดยมี Modularity เป็นคุณลักษณะย่อย [4] อาการของ Coupling ที่สูงเกินไปที่ Fowler เรียกว่า code smell ได้แก่การที่การแก้ไขหนึ่งจุดบังคับให้ต้องแก้ไขอีกหลายจุดตามไปด้วย (Shotgun Surgery) และการที่คลาสหนึ่งต้องรู้รายละเอียดภายในของอีกคลาสหนึ่งมากเกินจำเป็น [3]

**ตำแหน่งที่พบในโครงงาน** — วัดโดยลบคอมเมนต์ออกจากทุกบรรทัดก่อน แล้วค้นหาชื่อชนิดข้อมูลที่ประกาศในโมดูลอื่น ผลที่ได้มีทั้งด้านที่ดีและด้านที่ยังเป็นข้อจำกัด

ตารางที่ 2.2 ทิศทางการพึ่งพาระหว่างโมดูลที่วัดได้จากซอร์สโค้ด

### 2.1.3 สถาปัตยกรรมเชิงองค์ประกอบ (Component-Based Architecture)

สถาปัตยกรรมเชิงองค์ประกอบ หรือที่ในวงการพัฒนาเกมเรียกว่า Component Pattern คือการนิยามว่าอ็อบเจกต์หนึ่งในเกม "เป็นอะไร" ด้วย **ชุดของส่วนประกอบที่ถูกนำมาแปะไว้บนอ็อบเจกต์นั้น** แทนการนิยามด้วยคลาสที่สืบทอดกันเป็นลำดับชั้น Nystrom อธิบายว่าแบบแผนนี้เกิดขึ้นเพื่อแก้ปัญหาที่พบบ่อยในเกม คือเมื่อใช้การสืบทอด อ็อบเจกต์ที่ต้องการคุณสมบัติจากหลายสายพันธุ์พร้อมกันจะไม่มีที่ลงในลำดับชั้นเดียว และสุดท้ายโค้ดจะถูกยกขึ้นไปรวมกันในคลาสฐานจนคลาสฐานบวมผิดรูป [5] Gregory อธิบายโครงสร้างนี้ในบริบทของเอนจินเกมเชิงพาณิชย์ว่าเป็นโมเดลที่เอนจินยุคปัจจุบันส่วนใหญ่เลือกใช้ [6]

Unity ใช้โมเดลนี้เป็นสถาปัตยกรรมพื้นฐานของเอนจิน คือ `GameObject` เป็นเพียงภาชนะที่ไม่มีพฤติกรรมของตัวเอง พฤติกรรมทั้งหมดมาจาก Component ที่นำมาแปะ และสคริปต์ที่ผู้พัฒนาเขียนขึ้นจะกลายเป็น Component ได้ด้วยการสืบทอดจากคลาส `MonoBehaviour` [21]

**ตำแหน่งที่พบในโครงงาน** ตัวอย่างที่ชัดที่สุดคือระบบนาฬิกา ซึ่งเป็นระบบที่ใหญ่ที่สุดในโครงงาน (23 ไฟล์ 1,334 บรรทัด) นาฬิกาทั้ง 46 เรือนในฉากไม่ได้ถูกเขียนเป็นคลาสละเรือน แต่ประกอบขึ้นจากส่วนประกอบที่ทำหน้าที่ละอย่าง ได้แก่ `ClockMovement` (เก็บเวลา), `ClockDial` (แสดงเวลาด้วยเข็ม), `Mainspring` (แหล่งพลังงานที่ไขลานได้), `Pendulum` (ลูกตุ้มที่ถ้าถูกหยุดก็หยุดนาฬิกา), `ClockWinder` (ก้านไขลาน) และ `WeightChain` (โซ่ตุ้มถ่วง) ชนิดของนาฬิกาจึงเป็น **ผลรวมของส่วนประกอบที่แปะอยู่** ไม่ใช่คลาสลูกที่สืบทอดมา เช่น นาฬิกาที่ไม่มี `Mainspring` คือนาฬิกาที่ไม่มีวันหมดพลัง ซึ่งถูกต้องสำหรับนาฬิกาที่ใช้ตุ้มถ่วงหรือไฟบ้าน

ระบบสิ่งที่เปิดได้ใช้แนวทางเดียวกัน คือ `Openable` ถือสถานะเปิดหรือปิดและไม่ขยับอะไรเลย ส่วนการเคลื่อนไหวแยกเป็น `SwingMotion` (บานพับ) และ `SlideMotion` (เลื่อนตรง) ดังนั้นประตู ลิ้นชัก ฝาตู้โชว์ และผนังลับจึงใช้ `Openable` ตัวเดียวกันทั้งหมด

### 2.1.4 การประกอบแทนการสืบทอด (Composition over Inheritance)

หลักการ Composition over Inheritance ระบุว่าควรสร้างพฤติกรรมใหม่โดยการ **ประกอบ** อ็อบเจกต์ที่มีอยู่เข้าด้วยกัน แทนการ **สืบทอด** จากคลาสฐาน เหตุผลหลักคือการสืบทอดเป็นการผูกชนิดข้อมูลไว้ตั้งแต่ตอนคอมไพล์และสร้างความขึ้นต่อกันที่แน่นที่สุดแบบหนึ่งระหว่างคลาสลูกกับคลาสแม่ ขณะที่การประกอบเปลี่ยนได้ตอนรันไทม์และกระทบเฉพาะจุดที่ประกอบ [7] Gamma และคณะสรุปหลักนี้ไว้เป็นหนึ่งในสองหลักพื้นฐานของหนังสือ Design Patterns ว่า *"favor object composition over class inheritance"* [7]

**ตำแหน่งที่พบในโครงงาน** โครงงานนี้ปฏิบัติตามหลักนี้อย่างเคร่งครัดในระดับที่วัดได้เป็นตัวเลข ดังตารางที่ 2.3

## 2.2 หลักการออกแบบเชิงวัตถุที่ใช้ในโครงงาน

### 2.2.1 หลักการผกผันการพึ่งพา (Dependency Inversion Principle)

Dependency Inversion Principle (DIP) เป็นหนึ่งในหลัก SOLID ที่ Martin เสนอ มีใจความสองข้อ คือ (1) โมดูลระดับสูงต้องไม่ขึ้นต่อโมดูลระดับล่าง ทั้งสองควรขึ้นต่อสิ่งที่เป็นนามธรรม และ (2) สิ่งที่เป็นนามธรรมต้องไม่ขึ้นต่อรายละเอียด รายละเอียดต้องขึ้นต่อสิ่งที่เป็นนามธรรม [8] ผลที่ได้คือทิศทางการพึ่งพาถูก "ผกผัน" จากที่โค้ดไหลไปตามลำดับการเรียกใช้ กลายเป็นว่าทั้งผู้เรียกและผู้ถูกเรียกชี้เข้าหา interface ตัวกลางเดียวกัน Martin เรียกเส้นที่ interface นั้นสร้างขึ้นว่าเป็น **เส้นแบ่งเขตของสถาปัตยกรรม** (architectural boundary) [9]

**ตำแหน่งที่พบในโครงงาน** โครงงานนี้ใช้ DIP ผ่านรูปแบบที่เรียกได้ว่า *interface-based discovery* คือตัวควบคุมไม่ถือการอ้างอิงไปยังผู้ร่วมงานของตน แต่ค้นหาเอาเองตอนเริ่มทำงานด้วยเมธอดตระกูล `GetComponents<T>()` โดยระบุเป็น interface ไม่ใช่คลาสรูปธรรม จุดที่ใช้รูปแบบนี้มี 4 จุด เรียกว่า *seam* ของสถาปัตยกรรม ได้แก่ `IClockDisplay`, `IClockPart`, `ILock` และ `IPowerStore`

ตัวอย่างที่ชัดที่สุดคือ `ClockMovement` ซึ่งเป็นคลาสที่เก็บเวลาของนาฬิกา

```csharp
// Assets/Scripts/Clock/ClockMovement.cs:112-116
_displays = GetComponentsInChildren<IClockDisplay>(true);
// Inactive ones included: a part that is switched off is one the player has not
// fitted yet, and it has to be in the list so it can start saying no.
_parts = GetComponentsInChildren<IClockPart>(true);
```

คลาสนี้ **ไม่มีฟิลด์ชื่อ `dial`** และไม่รู้จักคลาส `ClockDial` เลย สิ่งที่มันรู้คือมีอะไรบางอย่างที่ implement `IClockDisplay` อยู่ภายใต้ตัวมัน และมันจะส่งจำนวนนาทีให้ทุกตัวในรายการนั้น ผลคือ `ClockMovement` (ระดับสูง) ไม่ขึ้นต่อ `ClockDial` (ระดับล่าง) แต่ทั้งสองขึ้นต่อ `IClockDisplay` ตรงตามใจความข้อแรกของ DIP

รูปแบบเดียวกันพบที่ `Openable` ซึ่งถามกลอนทุกตัวที่แปะอยู่กับตัวมัน

```csharp
// Assets/Scripts/Interaction/Openable.cs:20-35
private ILock[] Locks => _locks ?? (_locks = GetComponents<ILock>());
private ILock BlockingLock { get { foreach (ILock fitted in Locks) if (fitted.IsLocked) return fitted; return null; } }
```

และที่ `IPowerStore` ซึ่งถูกค้นหาโดยคลาสสามคลาสที่ไม่รู้จักกัน ด้วยบรรทัดที่เหมือนกันทั้งสามที่

```csharp
// ClockWinder.cs:59 · WeightChain.cs:36 · ClockStriker.cs:73
_power = movement.GetComponentInChildren<IPowerStore>(true);
```

ข้อสำคัญคือ interface เหล่านี้มีผู้ implement มากกว่าหนึ่งรายจริง ซึ่งเป็นสิ่งที่แยกการใช้ interface อย่างมีประโยชน์ออกจากการใช้ interface เกินความจำเป็น ดังตารางที่ 2.4

### 2.2.2 หลักการแยกส่วนต่อประสาน (Interface Segregation Principle)

Interface Segregation Principle (ISP) ระบุว่าไม่ควรบังคับให้ผู้ใช้งานต้องขึ้นต่อเมธอดที่ตนไม่ได้ใช้ interface ที่ใหญ่เกินไปควรถูกแยกออกเป็น interface เล็ก ๆ ตามกลุ่มผู้ใช้งาน [8]

**ตำแหน่งที่พบในโครงงาน** กรณีที่ชัดเจนที่สุดคือ `IActor` ซึ่งเป็นสัญญาที่กำหนดว่า "ผู้ที่มาโต้ตอบกับวัตถุ" สามารถถูกขอให้ทำอะไรได้บ้าง ทั้ง interface มีเพียงสามเมธอด

```csharp
// Assets/Scripts/Interaction/IActor.cs:15-26
public interface IActor
{
    void Say(string message);
    void OfferBag(IItemReceiver to);
    void Take(ItemData item);
}
```

และ `PlayerInteractor` implement ทั้งสามข้อด้วยโค้ดสามบรรทัด

```csharp
// Assets/Scripts/Player/PlayerInteractor.cs:105-109
public void Say(string message) => hud.ShowMessage(message);
public void OfferBag(IItemReceiver to) => inventoryUI.Open(to);
public void Take(ItemData item) => Inventory.Add(item);
```

ที่สำคัญคือเมธอด `IInteractable.Interact()` รับพารามิเตอร์เป็น `IActor` ไม่ใช่ `PlayerInteractor` (`Assets/Scripts/Interaction/Interactions.cs:13`) ดังนั้นวัตถุทุกชิ้นในเกม เช่น นาฬิกา ลิ้นชัก วงล้อรหัส จึงมองเห็นเพียงสามเมธอดที่มันต้องใช้ ไม่ได้มองเห็นระยะเอื้อม ความเร็วเดิน หรือระบบการยกของขึ้นดูของผู้เล่น ผลที่วัดได้มีสองอย่าง คือ (1) โมดูล `Clock` และ `Puzzle` สามารถใส่ `.asmdef` ที่ไม่อ้างถึงโมดูล `Player` ได้ และ (2) ทดสอบได้โดยไม่ต้องเปิดฉากและไม่ต้องมีผู้เล่นอยู่จริง ดังหลักฐานในหัวข้อ 2.4.2

### 2.2.3 หลักการเปิด–ปิด (Open–Closed Principle)

Open–Closed Principle (OCP) ซึ่ง Meyer เสนอไว้ครั้งแรก [10] และ Martin นำมาขยายในบริบทของ SOLID [8] ระบุว่าหน่วยซอฟต์แวร์ควร **เปิดให้ขยายได้ แต่ปิดการแก้ไข** กล่าวคือการเพิ่มความสามารถใหม่ควรทำได้ด้วยการเขียนโค้ดใหม่ ไม่ใช่การแก้โค้ดที่ทำงานอยู่แล้ว เพราะการแก้โค้ดเดิมมีความเสี่ยงที่จะทำให้สิ่งที่เคยทำงานได้เสียหาย

**ตำแหน่งที่พบในโครงงาน** เมื่อประเมินตามเกณฑ์นี้ โครงงานผ่าน 6 สถานการณ์จาก 9 สถานการณ์ ดังตารางที่ 2.5

สามสถานการณ์ที่ไม่ผ่านเกิดจากการเลือกใช้ `enum` ร่วมกับคำสั่ง `switch` แทนการใช้ polymorphism ซึ่งเป็น **การแลกเปลี่ยนที่ตัดสินใจโดยรู้ตัว** ไม่ใช่ความพลาด เกณฑ์ที่ใช้ตัดสินคือมิติที่คาดว่ามีค่าจำกัดและรู้ครบแล้ว (closed set) ใช้ `enum` ส่วนมิติที่คาดว่าจะเพิ่มขึ้นเรื่อย ๆ (open set) ใช้ interface ซึ่งเป็นเกณฑ์ที่ยอมรับได้ในทางวิศวกรรมซอฟต์แวร์ ยกเว้นกรณี `ICodeInput` ที่เจตนาเดิมต้องการให้เป็น open set แต่ผลลัพธ์ในโค้ดไม่เป็นเช่นนั้น

### 2.2.4 การแยกความกังวล (Separation of Concerns)

Separation of Concerns เป็นหลักที่ Dijkstra อธิบายไว้ว่าเป็นการพิจารณาเรื่องหนึ่ง ๆ แยกจากเรื่องอื่นในแต่ละครั้ง เพื่อให้สามารถใช้ความคิดกับเรื่องนั้นได้อย่างลึกซึ้งโดยไม่ถูกรบกวนจากเรื่องที่ไม่เกี่ยวข้อง [11] ในทางปฏิบัติของการออกแบบซอฟต์แวร์ หลักนี้แปลเป็นการแยกส่วนที่รับผิดชอบเรื่องต่างกันออกเป็นหน่วยต่างกัน

**ตำแหน่งที่พบในโครงงาน** โครงงานนี้ใช้หลักนี้อย่างสม่ำเสมอในสามคู่ที่สำคัญ

1. **แยกสถานะออกจากการเคลื่อนไหว** — `Openable` ถือสถานะเปิดหรือปิด ตรวจสอบกลอน และส่งสัญญาณเหตุการณ์ โดย **ไม่เขียนค่า `transform` เลยแม้แต่บรรทัดเดียว** (`Openable.cs:1-78`) ส่วน `SwingMotion` และ `SlideMotion` อ่านค่า `IsOpen` แล้วขยับวัตถุ โดยไม่รู้ว่าเหตุใดจึงเปิด (`SwingMotion.cs:25-31`, `SlideMotion.cs:25-30`)
2. **แยกเวลาออกจากการแสดงเวลา** — `ClockMovement` เก็บจำนวนนาทีและส่งค่าให้ผู้แสดงผล (`ClockMovement.cs:155-159`) ส่วน `ClockDial` แปลงนาทีเป็นมุมของเข็ม (`ClockDial.cs:22-37`) และ `DigitalReadout` แปลงนาทีเดียวกันเป็นตัวเลขสี่หลัก (`DigitalReadout.cs:44-57`) โดยสองคลาสหลังนี้ **ไม่ใช้โค้ดร่วมกันเลยแม้แต่บรรทัดเดียว**
3. **แยกตรรกะออกจากเสียง** — `TestRun` ควบคุมช่วงเวลาของการทดสอบนาฬิกา ส่วน `RunTicking` เล่นเสียงติ๊กโดยอ่านค่า `_run.Allows` เท่านั้นและ **ไม่มีตัวจับเวลาของตัวเอง** (`RunTicking.cs:39`) ทำให้เสียงไม่สามารถคลาดจากการทดสอบได้ ไม่ว่าจะตั้งความยาวของการทดสอบไว้เท่าใด

⚠️ **ข้อจำกัดที่ต้องระบุตามจริง** — การแยกนี้ทำได้สม่ำเสมอในโมดูล `Clock` และ `Interaction` แต่ **ไม่ได้ทำในสองจุด** คือ `Horologium.Update()` ขยับ `transform` ของจุดแสงด้วยตัวเอง (`Horologium.cs:94-106`) และ `InspectView` เรียกใช้ส่วนแสดงผลโดยตรง (`InspectView.cs:166,197,364-365`) รายละเอียดอยู่ในบทที่ 5 หัวข้อ 5.3

### 2.2.5 รูปแบบผู้สังเกตการณ์ (Observer Pattern)

Observer Pattern เป็นแบบแผนเชิงพฤติกรรมที่ Gamma และคณะนิยามไว้ว่า เป็นการกำหนดความสัมพันธ์แบบหนึ่งต่อหลายระหว่างอ็อบเจกต์ เพื่อให้เมื่ออ็อบเจกต์หนึ่งเปลี่ยนสถานะ อ็อบเจกต์ที่ขึ้นต่อทั้งหมดได้รับการแจ้งและปรับตัวเองอัตโนมัติ โดยที่ผู้แจ้งไม่จำเป็นต้องรู้ว่าใครเป็นผู้รับฟัง [7] ในภาษา C# แบบแผนนี้มีกลไกรองรับอยู่ในภาษาโดยตรงด้วยคำสั่ง `event` [20]

**ตำแหน่งที่พบในโครงงาน** โครงงานใช้ `event Action` ของ C# จำนวน 3 คู่ ดังตารางที่ 2.6 และ **ไม่ใช้ `UnityEvent` เลย**

ตารางที่ 2.6 การใช้ Observer Pattern ในโครงงาน

| ผู้ประกาศเหตุการณ์ | ผู้รับฟัง | ความหมายในเกม | หลักฐาน |

| `Openable.Opened` | `GameManager.HandleEscaped` | ประตูทางออกเปิด จึงจบเกม | `Openable.cs:37,76` · `GameManager.cs:25-26,42-47` |
| `IPowerStore.Filled` | `ClockStriker.Strike` | มีผู้เติมพลังงานให้นาฬิกา นกจึงออกมาขัน | `IPowerStore.cs:19` · `Mainspring.cs:25,46` · `ClockStriker.cs:76,106,110` |
| `ICodeInput.Changed` | `CodeLock.CheckWheels` | มีการหมุนวงล้อ จึงตรวจรหัสทันที | `CodeWheel.cs:30,63` · `CodeLock.cs:43,49,65-76` |

ตัวอย่างที่แสดงประโยชน์เชิงสถาปัตยกรรมของแบบแผนนี้ได้ชัดที่สุดคือคู่ที่สอง `ClockStriker` รับฟังเหตุการณ์ว่า "ถูกเติมพลังงาน" ไม่ได้รับฟังว่า "มีคนหมุนก้านไขลาน" ดังนั้นเมื่อนาฬิกาคุกคูถูกเปลี่ยนจากการไขลานด้วย `ClockWinder` ไปเป็นการดึงโซ่ตุ้มถ่วงด้วย `WeightChain` คลาส `ClockStriker` **ไม่ต้องถูกแก้เลยแม้แต่บรรทัดเดียว** เพราะทั้งสองคลาสเรียกเมธอด `IPowerStore.Fill()` เหมือนกัน (`ClockWinder.cs:100`, `WeightChain.cs:55`)

ข้อที่ควรบันทึกไว้ในแง่ความถูกต้องของการใช้งาน คือเหตุการณ์ทั้งสามคู่มีการยกเลิกการรับฟังใน `OnDisable` ครบทุกคู่ (`GameManager.cs:26`, `ClockStriker.cs:106`, `CodeLock.cs:46-50`) ซึ่งเป็นสิ่งจำเป็นเพื่อป้องกันการรั่วของหน่วยความจำและการเรียกเมธอดบนอ็อบเจกต์ที่ถูกทำลายไปแล้ว

### 2.2.6 การออกแบบที่ขับเคลื่อนด้วยข้อมูล (Data-Driven Design)

Data-Driven Design คือการย้ายสิ่งที่เคยเป็นค่าคงที่หรือตรรกะในซอร์สโค้ดออกมาเป็นข้อมูลภายนอก เพื่อให้เปลี่ยนแปลงได้โดยไม่ต้องคอมไพล์ใหม่ และเพื่อให้ผู้ที่ไม่ได้เขียนโปรแกรมสามารถปรับแต่งเนื้อหาได้ Gregory ระบุว่าแนวทางนี้เป็นสิ่งที่เอนจินเกมเชิงพาณิชย์ต้องมี เพราะงานออกแบบเกมมีการปรับค่าซ้ำจำนวนมากและรอบการคอมไพล์เป็นคอขวด [6]

**ตำแหน่งที่พบในโครงงาน** โครงงานใช้ `ScriptableObject` ของ Unity (ดูหัวข้อ 2.5.6) เป็นรูปแบบของข้อมูลภายนอก รวม 3 คลาส 12 ไฟล์แอสเซ็ต ได้แก่

- `ItemData` — นิยามว่าของชิ้นหนึ่งคืออะไร (10 ไฟล์ใน `Assets/Scenes/Items/`)
- `HousePlan` — ผังบ้านทั้งหลังในรูปข้อมูล คือสี่เหลี่ยมห้าห้องและรายการแนวผนังพร้อมจุดกลางของช่องเปิด (`Assets/Recipes/HousePlan.asset`)
- `ClockRecipe` — สูตรประกอบนาฬิกาหนึ่งชนิด (`Assets/Recipes/PlankClock.asset`)

กรณี `ClockRecipe` เป็นกรณีที่น่าสนใจที่สุด เพราะเป็นจุดที่ Data-Driven Design กับ Component-Based Architecture มาบรรจบกัน

```csharp
// Assets/Scripts/Clock/ClockRecipe.cs:19-37 — มีรายการเดียว ไม่แยกว่าอะไรคือจอแสดงผล อะไรคือส่วนประกอบ
[System.Serializable]
public struct Fitting { public GameObject Prefab; public Vector3 At; public Vector3 Turn; [Min(0.01f)] public float Scale; }

[SerializeField] private GameObject caseModel;   // ตัวเรือนเปล่า เป็นรูปทรงเท่านั้น
[SerializeField] private Fitting[] fittings;     // ทุกอย่างที่แปะลงบนเรือน เรียงลำดับใดก็ได้
```

สิ่งสำคัญของโครงสร้างนี้อยู่ที่สิ่งที่มัน **ไม่มี** คือไม่มีรายการแยกสำหรับจอแสดงผลและสำหรับส่วนประกอบ ทั้งสองเป็นเพียง "สิ่งที่นำมาแปะ" เหมือนกัน และ `ClockMovement` เป็นผู้แยกเองตอน `Awake` ด้วยการถามว่าสิ่งนั้น implement interface ใด ผลคือ **ชนิดของนาฬิกากลายเป็นไฟล์ข้อมูล ไม่ใช่เมธอดในโค้ด** ซึ่งพิสูจน์แล้วด้วยชุดทดสอบ `RecipeSeamTests.cs` (ดูหัวข้อ 2.4.2)

## 2.3 ทฤษฎีความถูกต้องของการนับเวลาในเกม

> หัวข้อนี้เป็นทฤษฎีที่รองรับปัญหาหลักที่พบระหว่างพัฒนา ซึ่งจะกล่าวถึงในบทที่ 5 หัวข้อ 5.2

### 2.3.1 วงรอบของเกมและความเป็นอิสระจากอัตราเฟรม

เกมแบบเรียลไทม์ทำงานด้วยโครงสร้างที่เรียกว่า **วงรอบของเกม (Game Loop)** คือวงวนที่ทำงานซ้ำไปเรื่อย ๆ โดยในแต่ละรอบจะรับข้อมูลนำเข้า ปรับสถานะของโลกในเกมให้ก้าวหน้าไปหนึ่งขั้น แล้ววาดภาพออกจอหนึ่งเฟรม Nystrom ชี้ว่าประเด็นสำคัญของวงรอบนี้คือวงวนทำงานด้วยความเร็วที่ไม่แน่นอน ขึ้นกับความสามารถของเครื่องและปริมาณงานในเฟรมนั้น ดังนั้นการปรับสถานะของโลกจึง **ต้องอ้างตามเวลาจริงที่ผ่านไป ไม่ใช่ตามจำนวนรอบของวงวน** [5]

ถ้าโค้ดปรับสถานะด้วยค่าคงที่ต่อหนึ่งเฟรม เช่น เพิ่มตำแหน่งขึ้นทีละ 0.1 หน่วยทุกเฟรม ผลลัพธ์จะผูกกับอัตราเฟรมของเครื่องที่รัน เครื่องที่วาดได้ 120 เฟรมต่อวินาทีจะเคลื่อนที่เร็วเป็นสองเท่าของเครื่องที่วาดได้ 60 เฟรมต่อวินาที อาการนี้เรียกว่าโค้ดที่ **ขึ้นกับอัตราเฟรม** (frame-rate dependent) และเป็นข้อผิดพลาดที่พบบ่อยที่สุดอย่างหนึ่งในการพัฒนาเกม วิธีแก้มาตรฐานคือคูณอัตราต่อวินาทีด้วยช่วงเวลาจริงของเฟรมนั้น ซึ่งใน Unity คือค่า `Time.deltaTime` ที่นิยามไว้ว่า *"ช่วงเวลาในหน่วยวินาทีจากเฟรมก่อนหน้ามาถึงเฟรมปัจจุบัน"* [13]

**ตำแหน่งที่พบในโครงงาน** การนับเวลาทุกจุดในโครงงานใช้ `Time.deltaTime` เป็นฐาน ตัวอย่างเช่น

```csharp
// Assets/Scripts/Clock/ClockMovement.cs:136
double advance = (double)minutesPerSecond * Rate * Time.deltaTime;
```

```csharp
// Assets/Scripts/Clock/Sandglass.cs:107 — นาฬิกาทรายนับเวลาที่ผ่านไป
_run = Mathf.Min(_run + Time.deltaTime, seconds);
```

```csharp
// Assets/Scripts/Clock/TestRun.cs:77
_ran += Time.deltaTime;
```

หลักฐานยืนยันเชิงลบที่มีน้ำหนัก คือการค้นหาคำว่า `Time.frameCount` ทั้งโครงงาน **ไม่พบการใช้งานเลยแม้แต่ที่เดียว** กล่าวคือไม่มีจุดใดในโครงงานที่นับเวลาด้วยจำนวนเฟรม

### 2.3.2 ความแม่นยำของเลขทศนิยมและความคลาดเคลื่อนสะสม

เลขทศนิยมแบบจุดลอยตัว (floating-point) ตามมาตรฐาน IEEE 754 เก็บค่าในรูปของแมนทิสซาคูณด้วยสองยกกำลังเลขชี้กำลัง ผลคือ **ระยะห่างระหว่างเลขที่แทนได้สองค่าที่อยู่ติดกัน ไม่คงที่ แต่ใหญ่ขึ้นตามขนาดของค่า** ระยะห่างนี้เรียกว่า ULP (Unit in the Last Place) [16] Goldberg อธิบายไว้ว่าผลสำคัญของคุณสมบัตินี้คือ เมื่อนำเลขขนาดใหญ่มากบวกกับเลขขนาดเล็กมาก ส่วนของเลขเล็กที่ตกอยู่ใต้ ULP ของผลลัพธ์จะถูกปัดทิ้งไปทั้งหมด ปรากฏการณ์นี้เรียกว่าการสูญเสียนัยสำคัญ (loss of significance) และจะสะสมตัวขึ้นเมื่อเกิดซ้ำหลายพันครั้ง [15]

ชนิดข้อมูล `float` ตามมาตรฐาน IEEE 754 binary32 มีแมนทิสซา 24 บิต ส่วน `double` (binary64) มี 53 บิต [16] เมื่อนำมาคำนวณกับค่าที่เกิดขึ้นจริงในโครงงานนี้ จะได้ผลตามตารางที่ 2.7

ตารางที่ 2.7 ระยะห่างระหว่างเลขที่แทนได้ ณ ค่าสะสม 280 นาที (เวลา 4:40)

| ชนิดข้อมูล | แมนทิสซา | ULP ณ ค่า 280 | การคำนวณ |
|---|---:|---:|---|
| `float` (binary32) | 24 บิต | ≈ 3.05 × 10⁻⁵ นาที | 2⁸ × 2⁻²³ = 2⁻¹⁵ |
| `double` (binary64) | 53 บิต | ≈ 5.68 × 10⁻¹⁴ นาที | 2⁸ × 2⁻⁵² = 2⁻⁴⁴ |

นาฬิกาในเกมนี้ทำงานโดยนำจำนวนนาทีที่เพิ่มขึ้นในหนึ่งเฟรมไปบวกกับจำนวนนาทีสะสมที่มีอยู่แล้ว ซึ่งเป็นรูปแบบของการอินทิเกรตค่าที่ละนิดเข้าสู่ผลรวมที่ใหญ่ขึ้นเรื่อย ๆ นับพันครั้งต่อการเล่นหนึ่งครั้ง จากตารางที่ 2.7 ULP ของ `float` ณ ค่า 280 อยู่ที่ประมาณ 3 × 10⁻⁵ นาที ขณะที่นาฬิกาในห้องโถงถูกตั้งค่า `minutesPerSecond` ไว้ที่ 1/60 ซึ่งที่อัตรา 60 เฟรมต่อวินาทีหมายถึงค่าที่เพิ่มขึ้นต่อเฟรมประมาณ 2.8 × 10⁻⁴ นาที กล่าวคือค่าที่นำมาบวกอยู่ห่างจาก ULP ของผลรวมเพียงประมาณหนึ่งลำดับความสำคัญเท่านั้น ซึ่งเป็นช่วงที่การปัดทิ้งเริ่มให้ผลที่วัดได้ และเลวร้ายลงอีกเมื่อนาฬิกาเดินช้า เพราะค่าที่เพิ่มต่อเฟรมยิ่งเล็กลง

หลักทั่วไปที่สรุปได้จากเรื่องนี้ และเป็นหลักที่ใช้ได้กับทุกระบบที่สะสมค่า คือ **ผลรวมที่กำลังสะสมและค่าที่นำมาบวกเข้าไป ต้องอยู่ภายในช่วงความแม่นยำของชนิดข้อมูลนั้นเมื่อเทียบกันเอง** ระบบใดที่อินทิเกรตค่าเล็กเข้าสู่ผลรวมใหญ่ต่อเนื่องหลายพันเฟรม ย่อมเผชิญปัญหาเดียวกัน

**ตำแหน่งที่พบในโครงงาน** `ClockMovement` เก็บจำนวนนาทีสะสมไว้ใน `double` ไม่ใช่ `float`

```csharp
// Assets/Scripts/Clock/ClockMovement.cs:50
private double _minutes;
```

โดยส่วนต่อประสานที่เปิดให้ภายนอกยังคงเป็น `float` (เมธอด `Minutes`, `Advance`, `Show`) เพราะการแปลงชนิดหนึ่งครั้งที่ปลายทางมีผลต่อความคลาดเคลื่อนเพียงประมาณ 0.01 องศาและเกิดครั้งเดียว ส่วนที่ทำใน `float` ไม่ได้คือ **การสะสม** ดังนั้นทุกอย่างที่บวกเข้ากับ `_minutes` จึงต้องอยู่ในรูป `double` ตลอดทาง รวมถึงการวนรอบ 12 ชั่วโมงด้วย เพราะเมธอด `Mathf.Repeat` ของ Unity รับเฉพาะ `float` จึงต้องทำการวนรอบในเมธอด `OnDial` แทน (`ClockMovement.cs:163-166`)

### 2.3.3 ลำดับการทำงานของฟังก์ชันเหตุการณ์

ใน Unity สคริปต์ที่สืบทอดจาก `MonoBehaviour` จะถูกเอนจินเรียกใช้ผ่านฟังก์ชันเหตุการณ์ (event function) ตามลำดับที่กำหนดไว้ในวงรอบของเฟรม โดยฟังก์ชันที่เกี่ยวข้องกับโครงงานนี้คือ `Awake` (เรียกครั้งเดียวเมื่อสร้างอ็อบเจกต์), `Update` (เรียกทุกเฟรม) และ `LateUpdate` (เรียกทุกเฟรม **หลังจาก** `Update` ของทุกสคริปต์ทำงานครบแล้ว) [14]

ประเด็นที่สำคัญต่อความถูกต้องของโปรแกรม และเป็นสิ่งที่เอกสารของ Unity ระบุไว้เป็นข้อจำกัดอย่างชัดเจน คือ **ลำดับการเรียกฟังก์ชันเหตุการณ์เดียวกันระหว่างอ็อบเจกต์ต่างกันนั้นไม่รับประกัน** เอกสารใช้ถ้อยคำว่า *"โดยทั่วไป ไม่สามารถเชื่อถือลำดับที่ฟังก์ชันเหตุการณ์เดียวกันถูกเรียกใช้สำหรับ GameObject ต่างกันได้ ยกเว้นในกรณีที่ลำดับนั้นถูกระบุไว้ในเอกสารหรือสามารถตั้งค่าได้"* และระบุต่อว่าลำดับระหว่างสคริปต์ต่างชนิดกันสามารถตั้งค่าได้ด้วย Script Execution Order แต่ลำดับระหว่างอินสแตนซ์ของสคริปต์เดียวกันนั้นตั้งไม่ได้เลย [14]

ผลที่ตามมาคือ หากสองส่วนประกอบที่ต้องทำงานเรียงลำดับกันเขียนโค้ดไว้ใน `Update` ทั้งคู่ โดยไม่ได้ตั้งค่า Script Execution Order ผลลัพธ์ของโปรแกรมจะไม่แน่นอน และอาจต่างกันในแต่ละเครื่องหรือแต่ละครั้งที่รัน วิธีแก้ที่ไม่ต้องพึ่งการตั้งค่าในโปรเจกต์ คือย้ายส่วนที่ต้องทำงานทีหลังไปอยู่ใน `LateUpdate` เพราะเอนจินรับประกันว่า `LateUpdate` ทำงานหลัง `Update` ของทุกสคริปต์

**ตำแหน่งที่พบในโครงงาน** คลาส `TestRun` ซึ่งควบคุมช่วงเวลาของการทดสอบนาฬิกา นับเวลาใน `LateUpdate` ขณะที่ `ClockMovement` เดินเข็มใน `Update`

```csharp
// Assets/Scripts/Clock/TestRun.cs:72-81
private void LateUpdate()
{
    if (!_running) return;
    _ran += Time.deltaTime;
    if (_ran >= Length) _running = false;
}
```

นอกจากนี้ยังมีกลไกที่เกี่ยวข้องอีกสองอย่างในโครงงาน คือ

1. **การคิดเฟรมสุดท้ายเป็นเศษส่วน** — `TestRun` คืนค่าตัวคูณอัตราเป็นสัดส่วนของเวลาที่เหลือต่อความยาวของเฟรมที่กำลังจะใช้ไป ทำให้เฟรมที่คร่อมเส้นสิ้นสุดถูกนับเพียงเท่าที่เหลือจริง เข็มจึงหยุดตรงขีดเดิมเสมอไม่ว่าเฟรมจะยาวเท่าใด

   ```csharp
   // Assets/Scripts/Clock/TestRun.cs:52
   public float RateScale => _running ? Mathf.Clamp01((Length - _ran) / Time.deltaTime) : 1f;
   ```

2. **การตั้งลำดับการทำงานของ `InputReader`** — คลาสนี้ใช้แอตทริบิวต์ `[DefaultExecutionOrder(-100)]` (`InputReader.cs:8`) เพื่อให้แน่ใจว่าอ็อบเจกต์ `PlayerControls` ถูกสร้างขึ้นก่อนที่คลาสอื่นจะเข้ามาลงทะเบียนรับฟังเหตุการณ์ใน `OnEnable` ของตนเอง ซึ่งเป็นการใช้กลไกตั้งลำดับอย่างตรงจุดในที่ที่จำเป็นจริง

## 2.4 ทฤษฎีการทดสอบซอฟต์แวร์

### 2.4.1 ระดับและชนิดของการทดสอบ

การทดสอบซอฟต์แวร์แบ่งตามขอบเขตของสิ่งที่ถูกทดสอบได้เป็นหลายระดับ โดยสองระดับที่เกี่ยวข้องกับโครงงานนี้คือ

- **Unit test** — ทดสอบหน่วยย่อยที่สุดของโค้ด เช่น เมธอดหรือคลาสเดียว โดยแยกออกจากสิ่งแวดล้อมภายนอกทั้งหมด Meszaros ระบุคุณสมบัติที่ unit test ที่ดีควรมีไว้ว่าต้องทำงานเร็ว ทำงานได้โดยไม่ต้องพึ่งระบบภายนอก และให้ผลเหมือนกันทุกครั้งที่รัน [17]
- **Integration test** — ทดสอบว่าหลายหน่วยทำงานร่วมกันได้ถูกต้อง ซึ่งจำเป็นต้องมีสิ่งแวดล้อมบางส่วนอยู่จริง

ใน Unity ความแตกต่างนี้สะท้อนออกมาเป็นสองโหมดของ Unity Test Framework คือ **EditMode test** ซึ่งรันในกระบวนการของตัวแก้ไข (Editor) โดยไม่ต้องเริ่มเกม และ **PlayMode test** ซึ่งรันในสภาพแวดล้อมเวลาทำงานจริงของเอนจิน จึงสามารถใช้ฟังก์ชันเหตุการณ์และให้เฟรมเดินไปข้างหน้าได้ [25] ความแตกต่างนี้สำคัญต่อการเขียนรายงานให้ถูกต้อง เพราะการทดสอบที่ต้องอาศัยการเดินของเฟรมนั้นไม่ใช่ unit test ตามความหมายที่เคร่งครัด

⚠️ **ข้อควรระวังสำหรับผู้เขียน** — โครงงานนี้มี **PlayMode test เท่านั้น** ไม่มี EditMode test และไม่มี unit test ที่รันนอกเอนจิน ในรายงานจึงต้องเรียกการทดสอบชุดนี้ว่า PlayMode test ทุกครั้ง **ห้ามเขียนว่าโครงงานมี unit test**

### 2.4.2 การทดสอบความเหมาะสมของสถาปัตยกรรม (Architecture Fitness Function)

Ford, Parsons และ Kua เสนอแนวคิด **Architecture Fitness Function** ว่าเป็นการทดสอบอัตโนมัติชนิดหนึ่งที่ไม่ได้ตรวจว่าฟังก์ชันคืนค่าถูกต้องหรือไม่ แต่ตรวจว่า **คุณลักษณะเชิงสถาปัตยกรรมที่ออกแบบไว้ยังเป็นจริงอยู่หรือไม่** ตัวอย่างเช่นการตรวจว่าโมดูลหนึ่งไม่อ้างถึงอีกโมดูลหนึ่ง หรือการตรวจว่าจุดต่อที่ออกแบบให้ขยายได้นั้นขยายได้จริง ประโยชน์ของการทดสอบชนิดนี้คือทำให้ข้ออ้างทางสถาปัตยกรรมกลายเป็นสิ่งที่ตรวจสอบได้โดยอัตโนมัติ ไม่ใช่เพียงข้อตกลงที่เขียนไว้ในเอกสารแล้วค่อย ๆ ถูกละเมิดไปตามเวลา [18]

**ตำแหน่งที่พบในโครงงาน** โครงงานมี PlayMode test รวม **15 กรณีใน 3 ไฟล์** และลักษณะของการทดสอบเหล่านี้ตรงกับนิยามของ Architecture Fitness Function มากกว่านิยามของ unit test ทั่วไป ดังตารางที่ 2.8

ตารางที่ 2.8 ไฟล์ทดสอบและคุณลักษณะเชิงสถาปัตยกรรมที่แต่ละไฟล์พิสูจน์

| ไฟล์ | บรรทัด | กรณี | พิสูจน์ว่า |
|---|---:|---:|---|
| `ActorSeamTests.cs` | 198 | 6 | `IActor` ตัดการพึ่งพาคลาส `PlayerInteractor` ได้จริง |
| `ClockSeamTests.cs` | 124 | 6 | `IClockDisplay` และ `IClockPart` เป็นจุดต่อที่ขยายได้จริง |
| `RecipeSeamTests.cs` | 71 | 3 | นาฬิกาที่ประกอบจากไฟล์ข้อมูลทำงานเหมือนที่เขียนด้วยโค้ด |

กรณีทดสอบที่แสดงลักษณะนี้ได้ชัดที่สุดสองกรณี คือ

**กรณีที่หนึ่ง** คลาสจอแสดงผลถูกประกาศขึ้นใหม่ **ภายในไฟล์ทดสอบ** ซึ่งหมายความว่าคลาสนี้ยังไม่มีอยู่ในขณะที่ `ClockMovement` ถูกคอมไพล์ หากการทดสอบผ่าน ย่อมพิสูจน์ได้ว่า `ClockMovement` ไม่ได้ผูกกับคลาสจอแสดงผลใดเป็นการเฉพาะ ซึ่งคือข้ออ้างของ DIP ในหัวข้อ 2.2.1 นั่นเอง

```csharp
// Assets/Tests/PlayMode/ClockSeamTests.cs:41-67
private class CountingDisplay : MonoBehaviour, IClockDisplay
{
    public int Shown; public float Last;
    public void Show(float minutes) { Shown++; Last = minutes; }
}

[UnityTest]
public IEnumerator A_display_written_after_the_movement_still_gets_the_time()
{
    GameObject go = Clock(out ClockMovement movement);
    var display = go.AddComponent<CountingDisplay>();
    Set(movement, "startHour", 4); Set(movement, "startMinute", 40);
    go.SetActive(true);
    yield return null;
    Assert.Greater(display.Shown, 0, "the movement never called Show");
    Assert.AreEqual(4 * 60 + 40, display.Last, 1f, "it was handed the wrong time");
}
```

**กรณีที่สอง** สัญญา `IActor` ทั้งสัญญาถูก implement ด้วยคลาส C# ธรรมดาความยาวประมาณสิบบรรทัด ที่ไม่ใช่ `MonoBehaviour` และไม่ต้องอยู่ในฉากใดเลย แล้วนำคลาสนั้นไปเปิดตู้ ไขกุญแจ และประกอบชิ้นส่วนนาฬิกาได้สำเร็จ ซึ่งพิสูจน์ข้ออ้างของ ISP ในหัวข้อ 2.2.2

```csharp
// Assets/Tests/PlayMode/ActorSeamTests.cs:18-27
private class RecordingActor : IActor
{
    public readonly List<string> Said = new List<string>();
    public readonly List<IItemReceiver> BagOfferedTo = new List<IItemReceiver>();
    public readonly List<ItemData> Taken = new List<ItemData>();
    public void Say(string message) => Said.Add(message);
    public void OfferBag(IItemReceiver to) => BagOfferedTo.Add(to);
    public void Take(ItemData item) => Taken.Add(item);
}
```

⚠️ **ข้อจำกัดที่ต้องระบุตามจริง** — ชุดทดสอบนี้ครอบคลุมเฉพาะโมดูล `Items`, `Interaction` และ `Clock` **ไม่มีกรณีทดสอบใดครอบคลุมโมดูล `Puzzle`, `World`, `Player`, `UI` หรือ `Game` เลย** และในกรณีของสามโมดูลหลัง เหตุผลเป็นข้อจำกัดทางเทคนิคของ Unity ที่ชุดทดสอบซึ่งมี `.asmdef` อ้างถึงโมดูลใน predefined assembly ไม่ได้ (ดูหัวข้อ 2.5.7) รายละเอียดอยู่ในบทที่ 4 และข้อเสนอแนะอยู่ในบทที่ 5 หัวข้อ 5.3

## 2.5 เทคโนโลยีที่ใช้ในการปฏิบัติงาน

### 2.5.1 Unity Engine

Unity เป็นเอนจินเกมสำหรับสร้างเนื้อหาสองมิติและสามมิติที่รองรับการส่งออกไปหลายแพลตฟอร์ม โครงสร้างพื้นฐานของเอนจินใช้โมเดล GameObject–Component ตามที่อธิบายไว้ในหัวข้อ 2.1.3 โดยหน่วยที่ใช้จัดองค์ประกอบของโลกในเกมเรียกว่า Scene และหน่วยที่ใช้เก็บแม่แบบของอ็อบเจกต์ที่นำกลับมาใช้ซ้ำเรียกว่า Prefab

โครงงานนี้ใช้ **Unity เวอร์ชัน 6000.3.5f2** โดยทั้งเกมอยู่ใน Scene เพียงหนึ่งฉาก คือ `Assets/Scenes/Main.unity` ขนาดประมาณ 2.35 เมกะไบต์ และเป็นฉากเดียวที่อยู่ในรายการ Build Settings ยืนยันจากไฟล์ `EditorBuildSettings.asset` ซึ่งมีรายการ `m_Scenes` เพียงรายการเดียว และจากเมธอด `GameManager.Restart()` (`Assets/Scripts/Game/GameManager.cs:30`) ที่เรียก `SceneManager.LoadScene` ด้วยหมายเลขของฉากที่กำลังทำงานอยู่ กล่าวคือโหลดฉากเดิมซ้ำ เพราะไม่มีฉากอื่นให้ไป

ผลของการใช้ฉากเดียวคือไม่ต้องมีระบบคงสถานะข้ามฉาก (ยืนยันจากการค้นหา `DontDestroyOnLoad` ได้ผลลัพธ์ศูนย์รายการ) แต่ก็หมายความว่าไม่มีระบบบันทึกและโหลดเกม และเมนูหลักเป็นแผงส่วนติดต่อผู้ใช้ภายในฉากเดียวกัน ไม่ใช่ฉากแยก

> **รูปที่ 2.2** หน้าต่าง Unity Editor ของโครงงาน — ให้เห็นหน้าต่าง Hierarchy, Scene View, Inspector และ Project พร้อมกันในภาพเดียว โดยเลือกอ็อบเจกต์ที่มีหลาย Component แปะอยู่ เช่น นาฬิกาเรือนหนึ่ง เพื่อให้ภาพนี้สื่อถึงโมเดล GameObject–Component ไปพร้อมกัน

### 2.5.2 Universal Render Pipeline (URP)

Universal Render Pipeline เป็นไปป์ไลน์การเรนเดอร์สำเร็จรูปที่สร้างขึ้นบน Scriptable Render Pipeline ของ Unity เอกสารของ Unity อธิบายไว้ว่า URP *"ให้ลำดับงานที่เป็นมิตรต่อศิลปิน ซึ่งช่วยให้สร้างกราฟิกที่ถูกปรับแต่งประสิทธิภาพแล้วได้อย่างรวดเร็วและง่ายดาย ครอบคลุมแพลตฟอร์มตั้งแต่อุปกรณ์พาหะไปจนถึงเครื่องเล่นเกมและเครื่องคอมพิวเตอร์ระดับสูง"* [19] ความแตกต่างที่สำคัญในทางปฏิบัติคือ URP ใช้เชดเดอร์และคุณสมบัติของวัสดุชุดของตนเอง ซึ่งไม่เข้ากันกับเชดเดอร์มาตรฐานของไปป์ไลน์แบบเดิม

โครงงานนี้ใช้ **URP เวอร์ชัน 17.3.0** ยืนยันจากไฟล์ `Packages/manifest.json` และจากไฟล์ตั้งค่า `Assets/Settings/UniversalRenderPipelineGlobalSettings.asset` และยืนยันในระดับการใช้งานจริงจากสองจุด คือวัสดุในโครงงานใช้คุณสมบัติชื่อ `_BaseMap` และ `_EmissionMap` ซึ่งเป็นชื่อคุณสมบัติของ URP และ `Assets/Scripts/Game/RoomLighting.cs:62` เรียกใช้ `RenderSettings.reflectionIntensity`

### 2.5.3 ภาษา C#

C# เป็นภาษาโปรแกรมเชิงวัตถุที่มีการตรวจชนิดข้อมูลตอนคอมไพล์ (statically typed) และทำงานบนสภาพแวดล้อมที่มีการจัดการหน่วยความจำอัตโนมัติ ข้อกำหนดของภาษาถูกรับรองเป็นมาตรฐาน ECMA-334 [20] Unity ใช้ C# เป็นภาษาเดียวสำหรับการเขียนสคริปต์

คุณสมบัติของภาษาที่โครงงานนี้ใช้อย่างมีนัยสำคัญต่อสถาปัตยกรรมมีสามข้อ

1. **`interface`** — ใช้เป็นสัญญากลางที่ทำให้เกิด DIP และ ISP ตามหัวข้อ 2.2.1 และ 2.2.2 รวม 12 interface
2. **`event`** — ใช้เป็นกลไกของ Observer Pattern ตามหัวข้อ 2.2.5 โครงงานใช้ `event Action` ของเนมสเปซ `System` และ **ไม่ประกาศ `delegate` ของตัวเองเลย** (ยืนยันจากการค้นหาคำว่า `delegate` ได้ผลลัพธ์ศูนย์รายการ)
3. **`double` กับ `float`** — ใช้แยกบทบาทกันตามหัวข้อ 2.3.2 คือใช้ `double` สำหรับการสะสมค่า และ `float` สำหรับส่วนต่อประสานที่เชื่อมกับเอนจิน

### 2.5.4 MonoBehaviour และวงจรชีวิตของส่วนประกอบ

`MonoBehaviour` เป็นคลาสฐานที่สคริปต์ของ Unity จำนวนมากสืบทอดมา เอกสารอ้างอิงของ Unity ระบุว่าคลาสนี้ *"มีฟังก์ชันวงจรชีวิตที่ทำให้การพัฒนาด้วย Unity ง่ายขึ้น"* และอ็อบเจกต์ของคลาสนี้ดำรงอยู่ในฐานะ Component ของ GameObject เสมอ [21] ฟังก์ชันวงจรชีวิตที่สำคัญและลำดับการเรียกใช้อธิบายไว้ในหัวข้อ 2.3.3

โครงงานนี้มีคลาสที่สืบทอดจาก `MonoBehaviour` ทั้งหมด **51 คลาสใน 51 ไฟล์** โดยทุกคลาสสืบทอดโดยตรงในระดับเดียวกัน ไม่มีคลาสใดสืบทอดจากคลาสอื่นในโครงงาน และลำดับของสมาชิกในแต่ละคลาสถูกจัดเรียงตามแบบแผนเดียวกันทุกไฟล์ คือค่าคงที่ ตามด้วยฟิลด์ที่ serialize ได้ ตามด้วยฟิลด์สถานะภายใน ตามด้วยเหตุการณ์และคุณสมบัติสาธารณะ ตามด้วยฟังก์ชันวงจรชีวิตเรียงตามลำดับการเรียกใช้ ตามด้วยเมธอดสาธารณะและเมธอดภายใน

### 2.5.5 Prefab

Prefab คือระบบของ Unity สำหรับเก็บ GameObject พร้อมส่วนประกอบ ค่าคุณสมบัติ และอ็อบเจกต์ลูกทั้งหมด ไว้ในรูปของแอสเซ็ตที่นำกลับมาใช้ซ้ำได้ เอกสารของ Unity อธิบายว่าแอสเซ็ต Prefab ทำหน้าที่เป็นแม่แบบที่ใช้สร้างอินสแตนซ์ของ Prefab ขึ้นในฉาก [22] และการแก้ไขที่แม่แบบจะส่งผลไปยังทุกอินสแตนซ์ที่ยังเชื่อมโยงอยู่

โครงงานนี้ใช้ Prefab เป็นหน่วยของการนำกลับมาใช้ซ้ำอย่างกว้างขวาง ตัวอย่างที่ชัดเจนที่สุดคือ `Assets/Prefabs/Clocks/ClockDial.prefab` ซึ่งเป็นหน้าปัดนาฬิกาที่ใช้ร่วมกันโดยนาฬิกาทุกเรือน พบอินสแตนซ์ของคลาส `ClockDial` ในฉากรวม **46 อินสแตนซ์** และ `Assets/Prefabs/Clocks/Parts/Mainspring.prefab` พบ 45 อินสแตนซ์

⚠️ **ข้อควรระวังในการอ้างตัวเลข** — เอกสารภายในโครงงาน (`CLAUDE.md`) ระบุว่ามีนาฬิกา 47 เรือน แต่การนับอินสแตนซ์ของส่วนประกอบ `ClockMovement` จากฉากจริงได้ **46** ในรายงานให้ใช้เลข 46 และระบุวิธีนับกำกับไว้ว่านับจากจำนวนอินสแตนซ์ของ `ClockMovement`

กลไกของ Prefab ยังเป็นที่มาของข้อผิดพลาดประเภทหนึ่งที่พบในโครงงานนี้ คือ **ค่าเริ่มต้นที่เขียนไว้ในซอร์สโค้ดของฟิลด์ที่มี `[SerializeField]` จะถูกเขียนทับด้วยค่าที่ถูก serialize ไว้ในแอสเซ็ตเสมอตอนที่ Unity โหลดอ็อบเจกต์** ดังนั้นการแก้ค่าเริ่มต้นในโค้ดจึงไม่มีผลต่อ Prefab ที่ถูกสร้างไปก่อนหน้านั้นแล้ว กรณีที่พบจริงในโครงงานและผลกระทบอยู่ในบทที่ 5 หัวข้อ 5.2

### 2.5.6 ScriptableObject

`ScriptableObject` เป็นชนิดข้อมูลของ Unity ที่สืบทอดจาก `UnityEngine.Object` และ serialize ได้ ต่างจาก `MonoBehaviour` ที่ว่า **อ็อบเจกต์ของมันไม่ได้แปะอยู่กับ GameObject ในฐานะ Component แต่ดำรงอยู่ในโปรเจกต์ในฐานะแอสเซ็ต เป็นอิสระจาก GameObject** เอกสารของ Unity ระบุว่าคุณค่าหลักของ `ScriptableObject` คือการเป็นที่เก็บข้อมูล และการใช้งานที่พบบ่อยคือการเป็นภาชนะสำหรับข้อมูลที่อ็อบเจกต์หลายตัวใช้ร่วมกันตอนทำงาน ซึ่งช่วยลดการใช้หน่วยความจำโดยหลีกเลี่ยงการทำสำเนาค่าเดียวกันหลายชุด [12]

โครงงานนี้ใช้ `ScriptableObject` เป็นกลไกของ Data-Driven Design ตามหัวข้อ 2.2.6 รวม 3 คลาส และ 12 ไฟล์แอสเซ็ต ได้แก่ `ItemData`, `HousePlan` และ `ClockRecipe`

### 2.5.7 Assembly Definition

Assembly Definition (ไฟล์นามสกุล `.asmdef`) เป็นกลไกของ Unity ที่ใช้แบ่งสคริปต์ในโปรเจกต์ออกเป็นแอสเซมบลีหลายชุด แทนที่จะคอมไพล์รวมอยู่ในแอสเซมบลีที่เอนจินสร้างให้โดยปริยาย (predefined assembly) ซึ่งมีชื่อว่า `Assembly-CSharp` ประโยชน์คือลดเวลาคอมไพล์เมื่อแก้โค้ด และ **ทำให้ขอบเขตการพึ่งพาระหว่างกลุ่มโค้ดกลายเป็นข้อบังคับระดับคอมไพเลอร์**

กฎการอ้างอิงที่สำคัญสามข้อซึ่งเอกสารของ Unity ระบุไว้อย่างชัดเจน คือ [23]

1. โดยปริยาย **predefined assembly อ้างอิงแอสเซมบลีอื่นทั้งหมด** รวมถึงแอสเซมบลีที่สร้างด้วย Assembly Definition เอกสารใช้ถ้อยคำว่า *"คลาสใน predefined assembly สามารถใช้ชนิดข้อมูลทั้งหมดที่นิยามไว้ในแอสเซมบลีอื่นใดในโปรเจกต์ได้"*
2. Unity **ไม่อนุญาต** ให้แอสเซมบลีที่สร้างด้วย Assembly Definition อ้างอิงไปยัง predefined assembly
3. Unity **ไม่อนุญาต** การอ้างอิงแบบวงจร (cyclical reference) คือกรณีที่สองแอสเซมบลีอ้างถึงกันไปกลับ เอกสารระบุว่าหากพบข้อผิดพลาดนี้ ต้องปรับโครงสร้างโค้ดเพื่อตัดวงจรออก หรือย้ายคลาสที่อ้างถึงกันไปอยู่ในแอสเซมบลีเดียวกัน

กฎข้อ 1 และ 2 ร่วมกันให้ผลที่มีประโยชน์เชิงสถาปัตยกรรมอย่างมาก คือ **การวางโค้ดชั้นล่างไว้ในไฟล์ `.asmdef` และวางโค้ดชั้นบนไว้ใน `Assembly-CSharp` เป็นการบังคับทิศทางการพึ่งพาให้เป็นทางเดียวโดยอัตโนมัติ** โดยไม่ต้องอาศัยวินัยของผู้เขียนโค้ด

**ตำแหน่งที่พบในโครงงาน** โครงงานใช้กลไกนี้ตรงตามรูปแบบที่กล่าวมา คือโมดูลชั้นล่างห้าโมดูลมี `.asmdef` ของตนเอง (`EscapeRoom.Items`, `EscapeRoom.Interaction`, `EscapeRoom.Clock`, `EscapeRoom.Puzzle`, `EscapeRoom.World`) ส่วนโมดูลชั้นบนสามโมดูล (`Player`, `UI`, `Game`) ถูกปล่อยไว้ใน `Assembly-CSharp` ผลคือการเขียนคำสั่งที่อ้างถึงคลาสของผู้เล่นจากภายในโมดูลนาฬิกา เช่น `GetComponent<PlayerMovement>()` ภายใน `ClockDial` **จะคอมไพล์ไม่ผ่าน** ตารางการพึ่งพาในหัวข้อ 2.1.2 จึงไม่ใช่เพียงข้อตกลง แต่เป็นข้อผิดพลาดของคอมไพเลอร์

เหตุผลที่ไม่แบ่ง `.asmdef` ให้ครบทั้งเก้าโมดูล มีข้อจำกัดทางเทคนิคบังคับอยู่สองข้อ

1. **มีวงจร `Player ⇄ UI` อยู่จริง** ซึ่งขัดกับกฎข้อ 3 โดยตรง สองโมดูลนี้จึงใส่ `.asmdef` แยกกันไม่ได้ ต้องตัดวงจรก่อน หรือรวมเป็นแอสเซมบลีเดียว
2. **ไฟล์ `PlayerControls.cs` อยู่ที่ `Assets/` ไม่ได้อยู่ใต้ `Assets/Scripts/`** หากสร้าง `EscapeRoom.Player.asmdef` ขึ้น คลาสในนั้นจะมองไม่เห็นคลาส `PlayerControls` เพราะอยู่ต่างแอสเซมบลีกัน และตามกฎข้อ 2 แอสเซมบลีใหม่นั้นจะอ้างถึง predefined assembly ที่ `PlayerControls` อยู่ไม่ได้ ต้องย้ายไฟล์ก่อน

⚠️ **ข้อจำกัดที่พบเพิ่มเติม** — ไฟล์ `EscapeRoom.Puzzle.asmdef` ประกาศการอ้างอิงไปยัง `EscapeRoom.Items` และ `EscapeRoom.Clock` แต่โค้ดในโฟลเดอร์ `Puzzle/` ไม่ได้ใช้ชนิดข้อมูลจากสองโมดูลนั้นเลย (รายการเดียวที่พบคือคำว่า `IClockDisplay` ในคอมเมนต์ที่ `ICodeInput.cs:5`) และ `EscapeRoom.Tests.asmdef` ประกาศอ้าง `EscapeRoom.Puzzle` ที่ไม่ได้ใช้เช่นกัน การประกาศเกินนี้ไม่กระทบการทำงาน แต่ทำให้ขอบเขตของโมดูลหลวมกว่าที่โค้ดต้องการจริง รายละเอียดอยู่ในบทที่ 5 หัวข้อ 5.3

> 📸 **คำแนะนำการแคปภาพ — ลบออกก่อนส่ง**
> **รูปที่ 2.4** หน้าต่าง Inspector ของไฟล์ `Assets/Scripts/Clock/EscapeRoom.Clock.asmdef` โดยให้เห็นช่อง Name และรายการ Assembly Definition References ที่มี `EscapeRoom.Items` และ `EscapeRoom.Interaction` อยู่
> คำบรรยาย: `รูปที่ 2.4 การประกาศขอบเขตการอ้างอิงของโมดูลนาฬิกาด้วยไฟล์ Assembly Definition`

### 2.5.8 Unity Input System

Unity Input System เป็นแพ็กเกจระบบรับข้อมูลนำเข้ารุ่นใหม่ของ Unity ที่แยกการกระทำในเกม (action) ออกจากอุปกรณ์และปุ่มที่ใช้สั่งการกระทำนั้น (binding) โดยนิยามไว้ในไฟล์ `.inputactions` และ Unity จะสร้างคลาส C# ให้อัตโนมัติจากไฟล์นั้น นอกจากนี้ยังมีแนวคิดของ **Action Map** คือกลุ่มของการกระทำที่เปิดหรือปิดพร้อมกันเป็นชุด [24]

โครงงานนี้ใช้ **Input System เวอร์ชัน 1.17.0** โดยคลาสที่ถูกสร้างอัตโนมัติคือ `Assets/PlayerControls.cs` และสถาปัตยกรรมการรับข้อมูลนำเข้าของโครงงานมีสองข้อตกลงที่สำคัญ

ข้อแรก **คลาส `InputReader` เป็นเจ้าของอ็อบเจกต์ `PlayerControls` เพียงตัวเดียวของเกมทั้งเกม** สร้างใน `Awake` และคืนทรัพยากรด้วย `Dispose()` ใน `OnDestroy` (`InputReader.cs:19-20`) เหตุผลคือเกมมีการสลับ Action Map สามชุด หากมีคลาสอื่นสร้างอ็อบเจกต์ `PlayerControls` ขึ้นอีกตัว Action Map ที่ตัวควบคุมโหมดเข้าใจว่าปิดไปแล้วจะยังเปิดอยู่

ข้อสอง **วิธีอ่านข้อมูลนำเข้าถูกเลือกตามชนิดของค่า** ดังตารางที่ 2.9

ตารางที่ 2.9 ข้อตกลงการอ่านข้อมูลนำเข้าตามชนิดของค่า

| ชนิดของค่า | ตัวอย่างในเกม | วิธีอ่าน | ตำแหน่งในโค้ด |
|---|---|---|---|
| ค่าต่อเนื่อง | การเดิน การหันมอง | เรียก `ReadValue()` ทุกเฟรม (polling) | `PlayerMovement.cs:43`, `MouseLook.cs:35` |
| เหตุการณ์การกดครั้งเดียว | ปุ่ม E, F, Q, Submit, Navigate | ลงทะเบียนรับฟังเหตุการณ์ `performed` | `PlayerInteractor.cs:51-52`, `InspectView.cs:121-123`, `InventoryUI.cs:43-45` |

เหตุผลเชิงวิศวกรรมของข้อตกลงนี้คือ ปุ่มที่อ่านด้วยการ polling ทุกเฟรมจะถูกอ่านซ้ำหรือถูกอ่านพลาด ขึ้นกับว่าเฟรมตกลงตรงจังหวะใดของการกด ขณะที่ค่าต่อเนื่องที่อ่านด้วยการรับฟังเหตุการณ์จะได้ค่าเฉพาะขณะที่ค่าเปลี่ยน ไม่ได้ค่าในขณะที่ผู้เล่นกดปุ่มค้างไว้

ข้อตกลงที่ตามมาอีกข้อหนึ่งคือ **การกระทำที่ถูกปิดจะคืนค่าโดยปริยาย (`default`) อยู่แล้ว จึงไม่ต้องล้างค่า แต่ค่าที่ถูกเก็บสะสมไว้ในฟิลด์ต้องถูกล้างใน `OnDisable`** มิฉะนั้นค่านั้นจะข้ามไปอยู่ในการเปิดใช้งานครั้งถัดไป โครงงานปฏิบัติตามข้อนี้จริงที่ `PlayerMovement.cs:59-63` (ล้างค่าความเร็วและความเร็วการตก), `HeadBob.cs:71-76`, `Flicker.cs:47-53`, `CuckooBird.cs:41-44` และ `RunTicking.cs:51-56`

### 2.5.9 Unity Test Framework และ NUnit

Unity Test Framework เป็นแพ็กเกจที่ใช้เขียนและรันการทดสอบอัตโนมัติใน Unity โดยสร้างอยู่บนเฟรมเวิร์ก **NUnit** ซึ่งเป็นเฟรมเวิร์กการทดสอบหน่วยสำหรับภาษาในตระกูล .NET [26] และรองรับการทดสอบสองโหมดตามที่อธิบายไว้ในหัวข้อ 2.4.1 คือ EditMode และ PlayMode [25]

โครงงานนี้ใช้ **Unity Test Framework เวอร์ชัน 1.6.0** ยืนยันจาก `Packages/manifest.json` และจากไฟล์ `Assets/Tests/PlayMode/EscapeRoom.Tests.asmdef` ซึ่งประกาศการอ้างอิงไปยัง `UnityEngine.TestRunner`, `UnityEditor.TestRunner` และ `nunit.framework.dll` พร้อมตั้งค่า `defineConstraints` เป็น `["UNITY_INCLUDE_TESTS"]` เพื่อให้แอสเซมบลีนี้ถูกคอมไพล์เฉพาะเมื่อมีการรวมชุดทดสอบเท่านั้น

กรณีทดสอบในโครงงานใช้แอตทริบิวต์ `[UnityTest]` ร่วมกับเมธอดที่คืนค่าชนิด `IEnumerator` และคำสั่ง `yield return null` ซึ่งเป็นรูปแบบที่ทำให้เฟรมเดินไปข้างหน้าหนึ่งเฟรมระหว่างการทดสอบ จำเป็นสำหรับการทดสอบสิ่งที่ทำงานใน `Update` และ `LateUpdate` ส่วนการตรวจผลลัพธ์ใช้คลาส `Assert` ของ NUnit

> 📸 **คำแนะนำการแคปภาพ — ลบออกก่อนส่ง**
> **รูปที่ 2.5** หน้าต่าง Test Runner ของ Unity (`Window > General > Test Runner`) แท็บ PlayMode ที่กางรายการกรณีทดสอบทั้ง 15 กรณีให้เห็นชื่อครบ **และแสดงผลว่าผ่านทั้งหมด**
> ⚠️ ภาพนี้ต้องรัน Test Runner เองก่อน เพราะผู้ช่วยวิจัยไม่ได้รับอนุญาตให้รันการทดสอบในโครงงาน ภาพเดียวกันนี้จะถูกใช้อ้างในบทที่ 4 ด้วย
> คำบรรยาย: `รูปที่ 2.5 ผลการรันชุดทดสอบ PlayMode ทั้ง 15 กรณีด้วย Unity Test Framework`

### 2.5.10 การสร้างเนื้อหาด้วยกระบวนวิธีและการเขียนสคริปต์สำหรับตัวแก้ไข

การสร้างเนื้อหาด้วยกระบวนวิธี (Procedural Content Generation หรือ PCG) คือการสร้างเนื้อหาของเกม เช่น ภูมิประเทศ ด่าน พื้นผิว หรือรูปทรง ด้วยอัลกอริทึม แทนการสร้างด้วยมือทีละชิ้น Hendrikx และคณะจัดหมวดเนื้อหาที่สร้างด้วยวิธีนี้ไว้หลายระดับ ตั้งแต่ระดับพื้นผิวและรูปทรง ไปจนถึงระดับการวางผังด่านและกฎของเกม [27] และ Shaker, Togelius กับ Nelson อธิบายว่าประโยชน์หลักของแนวทางนี้คือการลดต้นทุนการผลิตเนื้อหา และการทำให้เนื้อหาเปลี่ยนแปลงได้จากการแก้พารามิเตอร์ [28]

ในกรณีของ Unity การสร้างเนื้อหาด้วยกระบวนวิธีมักทำผ่านการเขียนสคริปต์สำหรับตัวแก้ไข (Editor Scripting) คือสคริปต์ที่ทำงานในตัวแก้ไขเท่านั้นและไม่ถูกรวมไปในเกมที่ส่งออก โดยวางไว้ในโฟลเดอร์ชื่อ `Editor` ซึ่งทำให้ Unity คอมไพล์เข้าแอสเซมบลี `Assembly-CSharp-Editor`

**ตำแหน่งที่พบในโครงงาน** โครงงานนี้มีเครื่องมือสร้างเนื้อหาในโฟลเดอร์ `Assets/Scripts/Editor/` รวม **11 ไฟล์ 5,772 บรรทัด** ซึ่งมากกว่าโค้ดส่วนรันไทม์ทั้งหมด (3,481 บรรทัด) โดยทุกตัวเลขบรรทัดในรายงานนี้นับเฉพาะบรรทัดที่ไม่ว่าง เครื่องมือเหล่านี้สร้างทั้งผังบ้าน รูปทรงของวัตถุ พื้นผิว และ Prefab โดยมีรายการตามตารางที่ 2.10

### 2.5.11 เครื่องมือพัฒนาอื่นและ Model Context Protocol

เครื่องมือพัฒนาอื่นที่พบหลักฐานการใช้งานในโครงงาน ได้แก่

1. **แพ็กเกจ uGUI เวอร์ชัน 2.0.0** ใช้สร้างส่วนติดต่อผู้ใช้ ยืนยันจากคำสั่ง `using UnityEngine.UI` และการใช้ชนิดข้อมูล `Text` แบบเดิม (legacy), `Graphic`, `Canvas` และ `RectTransform`
2. **ส่วนขยายสำหรับสภาพแวดล้อมการพัฒนา** คือ `com.unity.ide.rider` เวอร์ชัน 3.0.38 และ `com.unity.ide.visualstudio` เวอร์ชัน 2.0.26 และพบโฟลเดอร์ `.vscode/` ในโปรเจกต์
3. **Model Context Protocol (MCP)** เป็นมาตรฐานเปิดสำหรับเชื่อมต่อแอปพลิเคชันปัญญาประดิษฐ์เข้ากับระบบภายนอก เช่น แหล่งข้อมูล เครื่องมือ และลำดับงาน [29] โครงงานนี้ใช้แพ็กเกจ `com.coplaydev.unity-mcp` เพื่อเปิดช่องให้ควบคุม Unity Editor จากภายนอกผ่านโปรโตคอลนี้ ยืนยันจากไฟล์ `.mcp.json` ที่ตั้งค่าปลายทางไว้ที่ `http://127.0.0.1:8080/mcp`

⚠️ **ข้อควรระวังสำหรับผู้เขียน** — ไฟล์ `Packages/manifest.json` มีรายการ dependency รวม 46 รายการ แต่ส่วนใหญ่เป็นโมดูลที่ Unity ใส่มาตามแม่แบบของโปรเจกต์ ไม่ใช่การตัดสินใจทางเทคนิค โดยเฉพาะ `com.unity.ai.navigation`, `com.unity.timeline`, `com.unity.visualscripting` และ `com.unity.multiplayer.center` **ไม่พบการใช้งานในซอร์สโค้ดหรือในฉากเลย** (ยืนยันจากการค้นหา `using Unity.AI.Navigation`, `using UnityEngine.Timeline`, `NavMeshAgent` และ `PlayableDirector` ได้ผลลัพธ์ศูนย์รายการ) **ในรายงานห้ามเขียนว่าโครงงานใช้ NavMesh หรือ Timeline** และเทคโนโลยีที่เขียนลงบทที่ 2 ควรมีเฉพาะที่พบหลักฐานการใช้งานจริงตามหัวข้อ 2.5.1 ถึง 2.5.11 เท่านั้น
