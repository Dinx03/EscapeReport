# แผนแยกโมดูล — EscapeRoom

> เอกสารออกแบบ เขียนไว้ก่อนลงมือ
> คู่กับ [`MODULARITY.md`](MODULARITY.md) ซึ่งอธิบายว่า *ทำไม* ถึงเลือกนาฬิกาเป็นแกน
> ส่วนฉบับนี้อธิบายว่า *จะต่อชิ้นส่วนที่เหลือของโปรเจคเข้าด้วยกันยังไง*

---

## สรุปสั้น ๆ ก่อน

ตอนนี้ระบบนาฬิกาของเราเป็นโมดูลาร์จริง พิสูจน์แล้วด้วย แต่ **ส่วนที่เหลือของโปรเจคยังไม่ใช่**

ปัญหาไม่ได้อยู่ที่โค้ดเขียนไม่ดี ปัญหาอยู่ที่ **โมดูลพึ่งพากันไปมาเป็นวงกลม**
และไม่มีอะไรบังคับให้มันไม่พึ่งกัน — มีแค่ความตั้งใจของเราเองว่าจะไม่ทำ

เอกสารนี้เสนอ 4 ชิ้นที่ต้องเพิ่ม กับลำดับที่ควรทำ

> **สถานะล่าสุด:** ทำครบทั้งห้าชิ้นแล้ว ตรวจทุกชิ้น
> ชุดทดสอบ 13 ตัว ผ่านครบ · กราฟ dependency ถูกบังคับด้วยคอมไพเลอร์
> · ผังบ้านและชนิดนาฬิกาเป็นไฟล์ข้อมูลที่ดีไซเนอร์แก้ได้

---

## ทำไมต้องออกแบบก่อน ไม่ลงมือเลย

เพราะมีสองอย่างในแผนนี้ที่ **ทำผิดแล้วย้อนยาก**

**อย่างแรก** พอเราแบ่งโปรเจคเป็น assembly หลาย ๆ ตัวแล้ว การย้ายไฟล์จากโมดูลหนึ่งไปอีกโมดูลหนึ่ง
จะไม่ใช่แค่การลากไฟล์ในโฟลเดอร์อีกต่อไป มันกลายเป็นการแก้ว่า "โมดูลนี้พึ่งโมดูลไหนได้บ้าง"
ซึ่งกระทบทุกอย่างที่พึ่งมันอยู่ ตอนนี้ยังฟรี พอแบ่งแล้วมีราคา

**อย่างที่สอง** เราจะสร้างสิ่งที่เรียกว่า `IActor` ขึ้นมา
มันคือ "รายการสิ่งที่ของทุกชิ้นในเกมสั่งผู้เล่นให้ทำได้"
ถ้าใส่ความสามารถเกินไปตั้งแต่แรก แล้วอยากถอดออกทีหลัง
เราต้องไปแก้ทุกคลาสที่เกี่ยวข้อง ซึ่งตอนนี้มีอยู่สิบสี่จุด

ส่วนที่เหลือของแผน (ชิ้นที่ 3 กับ 4) ทำทีหลังได้เรื่อย ๆ ไม่เร่ง

## หลักการเดียวที่ใช้ทั้งแผน

ก่อนพูดถึงปัญหา ขอเริ่มจากของที่ **ทำเสร็จแล้วและใช้ได้จริง** ก่อน
เพราะทั้งแผนคือการเอารูปแบบนี้ไปใช้กับส่วนที่เหลือ

ลองดูตัวกลไกนาฬิกา `ClockMovement` มันทำหน้าที่เดียว คือเก็บ "ตอนนี้กี่โมง" ไว้เป็นตัวเลข
แล้วมันมีช่องเสียบอยู่สามช่อง

```
                        ┌─ ช่องเสียบ ────┐   ┌─ ใครเสียบได้บ้าง ────┐

                   ┌──► IClockDisplay ───►  ClockDial
                   │    "แสดงเวลาให้ที"     DigitalReadout
                   │
  ClockMovement ───┼──► IClockPart ──────►  Mainspring
  เก็บเวลาไว้        │    "ให้เดินมั้ย"        Pendulum
  ไม่รู้จักใครเลย     │
                   └──► IPowerStore ─────►  Mainspring
                        "เติมพลังงาน"
```

สิ่งที่อยากให้สังเกตมีสองอย่าง

**ลูกศรออกจากกลไกเสมอ ไม่มีลูกศรวิ่งเข้า** กลไกเป็นฝ่ายเรียกใช้ ไม่ใช่ฝ่ายถูกเรียก
และมันรู้จักแค่ "ช่อง" ไม่เคยรู้จัก "ของที่เสียบอยู่ในช่อง"
เราจึงเพิ่ม `DigitalReadout` เข้าไปได้โดยไม่ต้องแก้กลไกแม้แต่บรรทัดเดียว

**ของชิ้นเดียวเสียบได้หลายช่อง** สังเกตว่า `Mainspring` โผล่สองที่
เพราะมันเป็นทั้งชิ้นส่วนที่มีสิทธิ์บอกว่า "นาฬิกาหยุดนะ" และเป็นที่เก็บพลังงานไปด้วย

> **กฎที่ได้จากตรงนี้**
> ถ้าอยากให้คนอื่นต่อของใหม่เข้ากับของเราได้ โดยไม่ต้องมาแก้ของเรา —
> ของเราต้องรู้จักแค่ "ช่อง" ไม่ใช่รู้จักตัวของที่จะมาเสียบ
>
> ที่เหลือของเอกสารนี้คือการเอากฎข้อนี้ไปใช้กับ **โมดูล** แทนที่จะใช้กับ **คลาส**

## ปัญหาตอนนี้: ทุกอย่างพึ่งกันไปมา

ลองนึกภาพว่าวันหนึ่งเราอยากยกระบบนาฬิกาทั้งชุดไปใช้ในเกมอื่น
เราลากโฟลเดอร์ `Clock/` ไป แล้วมันจะคอมไพล์ไม่ผ่านทันที
เพราะทุกไฟล์ในนั้นอ้างถึงคลาสผู้เล่นของเกมนี้

แล้วมันอ้างไปทำอะไร? **แค่สามอย่าง**

- อยากขึ้นข้อความบนจอ → `interactor.Hud.ShowMessage(...)`
- อยากเปิดกระเป๋าให้ผู้เล่นเลือกของ → `interactor.OpenInventoryFor(...)`
- อยากยัดของเข้ากระเป๋า → `interactor.Inventory.Add(...)`

เพื่อสามอย่างนี้ นาฬิกาต้องรู้จักผู้เล่นทั้งคลาส — รู้จักความเร็วเดิน รู้จักระยะเล็ง
รู้จักระบบมองใกล้ ๆ รู้จักทุกอย่าง ทั้งที่ไม่เคยใช้เลย

```
   ตอนนี้                             เป้าหมาย

   Player ⇄ Interaction              Game
     ▲   ╲       ▲                     ↓
     │    ╲      │                   Player ──► UI
   Clock  Puzzle ┘                     ↓
                                     Clock  Puzzle
   ── เส้นแดง 3 เส้น ──                   ↓      ↓
   Interaction ──► Player            Interaction
   Clock ────────► Player                ↓
   Puzzle ───────► Player            Items
                                     (ลูกศรชี้ลงทางเดียว)
```

สิ่งที่แย่กว่านั้นคือ **ตอนนี้เราไม่มีอะไรบังคับเลย**
ทั้งโปรเจคอยู่ใน assembly เดียว ถ้าพรุ่งนี้มีคนมาเขียน
`GetComponent<PlayerMovement>()` ลงไปใน `ClockDial` มันก็คอมไพล์ผ่านเฉย ๆ
ไม่มีอะไรเตือน

แปลว่าตอนนี้เราพูดกับอาจารย์ได้แค่ *"ผมพยายามไม่ให้มันพึ่งกัน"*
ยังพูดไม่ได้ว่า *"มันพึ่งกันไม่ได้"* — สำหรับงานวิจัย ความต่างตรงนี้คือทุกอย่าง

## ชิ้นที่ 1 · `IActor` — บอกผู้เล่นเท่าที่จำเป็น ✅ **ทำแล้ว**

> **ผลจริงหลังทำเสร็จ**
>
> แตะ 13 ไฟล์ · เพิ่มใหม่ 1 (`IActor.cs`) · ย้าย 2 (`InspectView`, `BorrowedProp` → `Player/`)
> ตรงตามที่ประเมินไว้ทุกตัว
>
> กราฟ dependency หลังแก้ (นับเฉพาะโค้ดจริง ไม่นับคอมเมนต์):
>
> ```
> Items        →  (ไม่พึ่งใคร)
> Interaction  →  Items
> Clock        →  Items, Interaction        ← ไม่พึ่ง Player แล้ว
> Puzzle       →  Interaction               ← ไม่พึ่ง Player แล้ว
> Player       →  Items, Interaction, UI
> UI           →  Items, Player
> Game         →  Interaction, Player
> World        →  (ไม่พึ่งใคร)
> ```
>
> เหลือวงเดียวคือ `Player ⇄ UI` ซึ่ง**ตั้งใจให้เหลือ** — สองกล่องนี้จะรวมเป็น assembly
> เดียวกันตามแผนอยู่แล้ว HUD ที่ห้ามเอ่ยชื่อ mode controller ที่มันสังกัด
> คือรอยต่อที่ไม่มีอะไรอยู่อีกฝั่ง
>
> ทดสอบแล้ว: องก์ 1–5 ผ่านครบ ล็อกทั้งห้าตัวเด้งเปิดจริง และการหยิบของ
> (`Take` + `Say`) ทำงาน — ทั้งหมดเรียกผ่าน `IActor` อย่างเดียว ไม่มีที่ไหนแตะ
> `PlayerInteractor` อีกแล้ว

แทนที่จะให้ของทุกชิ้นในเกมรู้จักผู้เล่นทั้งตัว
เราเขียน "ใบสั่งงาน" สั้น ๆ ขึ้นมาใบหนึ่ง แล้วให้ทุกคนคุยกันผ่านใบนี้

```csharp
// ใครก็ได้ที่กำลังใช้งานของชิ้นนี้อยู่ — ผู้เล่น, NPC, หรือชุดทดสอบ
public interface IActor
{
    void Say(string message);        // ขึ้นข้อความให้ที
    void OfferBag(IItemReceiver to); // เปิดกระเป๋าให้เลือกของ
    void Take(ItemData item);        // เอาของนี้ไป
}
```

แล้วเปลี่ยนลายเซ็นจาก `Interact(PlayerInteractor)` เป็น `Interact(IActor)`

**จุดสำคัญคือลูกศรกลับทิศ**

```
   ก่อน                                  หลัง

   ClockWinder ──► PlayerInteractor      ClockWinder ──► IActor
                   ├ Hud                                    ▲
                   ├ Inventory                              │ implements
                   ├ InspectView                            │
                   ├ reach, aimAssist              PlayerInteractor
                   └ ... อีกเพียบ

   นาฬิกาวิ่งไปหาผู้เล่น                    ทั้งคู่วิ่งไปหาข้อตกลงตรงกลาง
                                          ไม่มีใครรู้จักใครอีกต่อไป
```

เดิมนาฬิกาวิ่งไปหาผู้เล่น หลังแก้ **ทั้งนาฬิกาและผู้เล่นวิ่งไปหาข้อตกลงตัวเดียวกัน**
ไม่มีใครรู้จักใครอีกต่อไป นี่คือสิ่งที่ทำให้ `Clock` เลิกพึ่ง `Player` ได้

### ผลพลอยได้ที่สำคัญกับงานวิจัย

พอทำแบบนี้แล้ว เราเขียนชุดทดสอบที่ "กดใช้นาฬิกา" ได้ **โดยไม่ต้องมีผู้เล่นในฉากเลย**
แค่ทำคลาสทดสอบเล็ก ๆ ที่รับใบสั่งงานใบเดียวกัน แล้วจดว่ามันถูกสั่งให้พูดอะไรบ้าง

นี่คือหลักฐานที่ *รันได้* ว่าโมดูลแยกกันจริง ซึ่งดีกว่าคำอธิบายบนกระดาษมาก

## ดูใกล้ ๆ · `Clock` กับ `Interaction` จะหน้าตาแบบไหน

สองกล่องนี้เป็นคู่ที่ใหญ่ที่สุดในโปรเจค (17 กับ 9 ไฟล์) และเป็นคู่ที่แสดงหลักการได้ชัดที่สุด
เลยขอลงรายละเอียดตรงนี้หน่อย

### `Interaction` คือคลังคำศัพท์

มันไม่รู้จักนาฬิกา ไม่รู้จักปริศนา รู้แค่ว่า "ผู้เล่นทำอะไรกับของได้บ้าง"
แล้วประกาศออกมาเป็นคำศัพท์กลาง

| คำศัพท์ | แปลว่า |
|---|---|
| `IInteractable` | กด **E** ใส่ได้ |
| `IInspectable` | กด **F** ดูใกล้ ๆ ได้ |
| `IItemReceiver` | เอาของจากกระเป๋ามาใช้กับมันได้ |
| `ILock` | ล็อกของที่เปิดได้เอาไว้ |
| `IActor` **(เพิ่มใหม่)** | ใครก็ได้ที่กำลังใช้งานของชิ้นนี้อยู่ |

บวกของใช้จริงอีกสามชิ้น — `Openable` (สิ่งที่เปิดได้ แต่ขยับเองไม่เป็น),
`SwingMotion` (บานพับ), `SlideMotion` (เลื่อน)

**`IActor` ต้องอยู่กล่องนี้** ไม่ใช่กล่อง Player เพราะทั้ง Clock และ Puzzle
พึ่ง Interaction อยู่แล้ว วางไว้ตรงนี้ทุกคนหยิบไปใช้ได้โดยไม่เกิดเส้นพึ่งพาเส้นใหม่

### `Clock` คือคนที่พูดคำศัพท์นั้น

```
   ┌─ Interaction ─────────────┐          ┌─ Clock ────────────────────────────┐
   │                           │          │                                    │
   │  IInteractable  ◄─────────┼──────────┼── ClockWinder                      │
   │                           │  4 คลาส   │   WeightChain                      │
   │                           │          │   ClockSetter                      │
   │                           │          │   ClockPartSocket                  │
   │                           │          │                                    │
   │  IItemReceiver  ◄─────────┼──────────┼── ClockPartSocket                  │
   │                           │  1 คลาส   │                                    │
   │                           │          │                                    │
   │  ILock          ◄─────────┼──────────┼── TimeLock                         │
   │                           │  2 คลาส   │   RunningLock                      │
   │                           │          │                                    │
   │  Openable       ◄─────────┼──────────┼── ClockStriker (เปิด/ปิดช่องนก)       │
   │                           │  1 ที่    │                                    │
   │  IActor  (ใหม่)  ◄─────────┼──────────┼── ทุกตัวข้างบนรับเป็นพารามิเตอร์      │
   │                           │          │                                    │
   │  SwingMotion              │          │  ── คำศัพท์ของตัวเอง ──────────────  │
   │  SlideMotion              │          │  IClockDisplay ◄─ ClockDial         │
   │  KeyLock                  │          │                   DigitalReadout    │
   │  PickupItem               │          │  IClockPart    ◄─ Mainspring        │
   │  Inspectable              │          │                   Pendulum          │
   │                           │          │  IPowerStore   ◄─ Mainspring        │
   │  ไม่รู้จัก Clock เลยสักบรรทัด  │          │                                    │
   └───────────────────────────┘          └────────────────────────────────────┘

              ลูกศรวิ่งทางเดียว — จาก Clock ไป Interaction เท่านั้น
```

**จุดเชื่อมมีแค่ 5 จุด** และทุกจุดเป็น Clock วิ่งไปหา Interaction ไม่มีย้อนกลับ

### ที่ modular จริง ๆ คือตรงนี้

**Interaction ไม่เคยเรียนรู้คำว่า "นาฬิกา"** — `Openable` ถามทุก `ILock` ที่ติดอยู่กับมันว่า
"เปิดได้มั้ย" มันไม่รู้เลยว่าคำตอบมาจากกุญแจ จากรหัส จากเวลาบนหน้าปัด
หรือจากนาฬิกาที่กำลังเดินอยู่

ผลที่ได้จริงในเกม:

- ตู้ที่ต้องทั้งกุญแจ**และ**รหัส = ใส่ `KeyLock` + `CodeLock` สองตัว ไม่ต้องเขียนคลาสใหม่
- อยากได้ล็อกที่เปิดเมื่อนาฬิกาเดิน = เขียน `RunningLock` ไฟล์เดียว `Openable` ไม่รู้เรื่องเลย
- ประตูที่เลื่อนขึ้นแทนบานเปิด = สลับ `SwingMotion` เป็น `SlideMotion` ชี้ขึ้น

และ **Clock มีคำศัพท์ของตัวเองอีกชั้น** ที่ Interaction ไม่รู้จักเลย —
นี่คือสิ่งที่ทำให้มันเป็นโมดูลจริง ๆ ไม่ใช่แค่กองไฟล์
ข้างในมันมีชีวิตของตัวเอง กลไกยื่นเวลาให้จอ ชิ้นส่วนมีสิทธิ์ยับยั้ง
ที่เก็บพลังงานถูกเติมโดยอะไรก็ได้

### แล้วต้องแก้อะไรจริง ๆ บ้าง

น้อยกว่าที่คิด — **แตะ 13 ไฟล์ เพิ่มใหม่ 1 ไฟล์ ย้าย 2 ไฟล์**

| ที่ไหน | ทำอะไร | กี่ไฟล์ |
|---|---|---|
| `Interaction/` | เพิ่ม `IActor.cs` | +1 |
| `Interaction/` | เปลี่ยนลายเซ็นเป็น `IActor` — `Interactions`, `Openable`, `KeyLock`, `PickupItem` | 4 |
| `Interaction/` | ย้ายไป `Player/` — `InspectView`, `BorrowedProp` | 2 |
| `Clock/` | เปลี่ยนลายเซ็น — `ClockWinder`, `WeightChain`, `ClockSetter`, `ClockPartSocket`, `TimeLock`, `RunningLock` | 6 |
| `Puzzle/` | เปลี่ยนลายเซ็น — `CodeLock`, `CodeWheel` | 2 |

การเปลี่ยนแต่ละไฟล์คือแก้บรรทัดเดียวเป็นส่วนใหญ่

```csharp
// เดิม
public void Interact(PlayerInteractor interactor)
{
    interactor.Hud.ShowMessage("ไขลานแล้ว");
}

// ใหม่
public void Interact(IActor actor)
{
    actor.Say("ไขลานแล้ว");
}

ส่วน `BorrowedProp` ที่ต้องย้ายตามไปด้วย เพราะมันถูกใช้โดย `InspectView` ที่เดียวเท่านั้น

## ชิ้นที่ 2 · `asmdef` — เปลี่ยนความตั้งใจให้เป็นกฎ ✅ **เสร็จ · พิสูจน์แล้ว**

> **แผนเปลี่ยนระหว่างทาง — และเปลี่ยนไปในทางที่ดีกว่า**
>
> เจอสองอย่างที่ทำให้แผนเดิม (แยก 6 assembly) ทำไม่ได้ตรง ๆ:
>
> 1. **`PlayerControls.cs` อยู่ที่ `Assets/` ไม่ใช่ใน `Scripts/`** — ถ้าแยก `Player`
>    เป็น assembly ของตัวเอง มันจะอ้าง `PlayerControls` ที่อยู่ใน `Assembly-CSharp` ไม่ได้
>    (asmdef อ้าง predefined assembly ไม่ได้) ต้องย้ายไฟล์ input ซึ่งเสี่ยงกับ
>    generated-path ที่ฝังอยู่ใน importer
> 2. **`Player ⇄ UI` เป็นวงจริง** และ assembly เป็นวงไม่ได้เลย — เป็น hard error
>
> **ทางที่เลือกแทน: แยกเฉพาะชั้นล่าง** ห้ากล่อง — `Items`, `Interaction`, `Clock`,
> `Puzzle`, `World` — ส่วน `Player`, `UI`, `Game`, `Editor` ปล่อยไว้ใน `Assembly-CSharp`
> ตามเดิม
>
> ได้ผลเท่ากันเป๊ะ เพราะ **`Assembly-CSharp` อ้าง asmdef ได้ แต่ asmdef อ้าง
> `Assembly-CSharp` ไม่ได้** — คอมไพเลอร์จึงห้าม `Clock` แตะ `Player` โดยอัตโนมัติ
> โดยไม่ต้องแตะไฟล์ input และไม่ต้องแก้วง `Player ⇄ UI`
>
> ```
> Assets/Scripts/Items/EscapeRoom.Items.asmdef              refs: —
> Assets/Scripts/Interaction/EscapeRoom.Interaction.asmdef  refs: Items
> Assets/Scripts/Clock/EscapeRoom.Clock.asmdef              refs: Items, Interaction
> Assets/Scripts/Puzzle/EscapeRoom.Puzzle.asmdef            refs: Items, Interaction, Clock
> Assets/Scripts/World/EscapeRoom.World.asmdef              refs: —
>
> Player · UI · Game · Editor  →  ยังอยู่ Assembly-CSharp (ชั้นบนสุด เห็นทุกอย่าง)
> ```
>
> **ยังไม่ได้ verify** เพราะ Unity หลุดการเชื่อมต่อ ตรวจแบบ static แล้วว่า
> ห้ากล่องนี้ไม่อ้าง `UnityEditor`, `UnityEngine.UI`, `InputSystem`
> และไม่อ้างชื่อคลาสใด ๆ ใน `Player/`, `UI/`, `Game/` เลยสักจุด
>
> **ผลจริงหลัง Unity คอมไพล์** — อ่านออกมาจาก DLL ที่ Unity สร้างเอง
> (`Library/ScriptAssemblies/`) ไม่ใช่จากการอ่านโค้ด:
>
> ```
> EscapeRoom.Items        →  (ไม่อ้างใคร)
> EscapeRoom.Interaction  →  Items
> EscapeRoom.Clock        →  Items, Interaction
> EscapeRoom.Puzzle       →  Interaction
> EscapeRoom.World        →  (ไม่อ้างใคร)
>
> Assembly-CSharp (Player · UI · Game)  →  อ้าง EscapeRoom.* ได้   ← ทางเดียว
> ```
>
> **ไม่มี DLL ไหนในห้าตัวนี้มีคำว่า `Assembly-CSharp` อยู่เลย** — `Clock` แตะ `Player`
> ไม่ได้แล้ว ไม่ใช่เพราะเราตั้งใจ แต่เพราะคอมไพเลอร์ไม่ยอม
>
> ไม่มี `error CS` ใน Editor.log และ DLL ทั้งหกตัวมี timestamp ใหม่กว่าไฟล์ที่แก้


Unity มีไฟล์ชนิดหนึ่งชื่อ `.asmdef` (Assembly Definition)
หน้าที่ของมันคือประกาศว่า "โฟลเดอร์นี้เป็นโมดูลหนึ่ง และพึ่งโมดูลไหนได้บ้าง"

พอวางไฟล์นี้ลงไปหกจุด **คอมไพเลอร์จะบังคับให้เอง**
ใครเขียนผิดกฎ โปรเจคจะไม่คอมไพล์ ไม่ต้องรอให้คนมารีวิว

| โมดูล | พึ่งอะไรได้ | ห้ามพึ่ง | เพราะอะไร |
|---|---|---|---|
| `Items` | — | ทุกอย่าง | เป็นคำศัพท์ร่วมที่คนอื่นใช้ ต้องไม่พึ่งใคร |
| `Interaction` | Items | Player, UI | เป็น *ที่อยู่ของข้อตกลง* ไม่ใช่ *ผู้ใช้ข้อตกลง* |
| `Clock` | Items, Interaction | Player, UI, Puzzle | ต้องยกไปโปรเจคอื่นได้ |
| `Puzzle` | Items, Interaction, Clock | Player, UI | เหตุผลเดียวกัน |
| `Player` | ทั้งหมดข้างบน + UI | Game | โมดูลเดียวที่รู้ว่า "ผู้เล่น" คืออะไร |
| `Game` | ทั้งหมด | — | ชั้นบนสุด หน้าที่คือประกอบทุกอย่างเข้าด้วยกัน |

### มีอย่างหนึ่งที่ต้องย้ายก่อน

ไฟล์ `InspectView.cs` ตอนนี้อยู่ในโฟลเดอร์ `Interaction/`
แต่ถ้าเปิดดูข้างในจะเห็นว่ามันถือ `InputReader` กับ `PlayerModeController` เอาไว้
— มันเป็นกลไกฝั่งผู้เล่นมาตั้งแต่แรก แค่วางผิดที่

**ย้ายมันไป `Player/`** แล้ว `Interaction` จะไม่เหลือการอ้างถึง `Player` เลยสักจุด

### ผลพลอยได้ที่รู้สึกได้ทุกวัน

แก้สคริปต์นาฬิกาทีหนึ่ง Unity จะคอมไพล์ใหม่แค่ assembly เดียว ไม่ใช่ทั้งโปรเจค
รอสั้นลงมาก

## ชิ้นที่ 3 · `ClockRecipe` — ให้ดีไซเนอร์สร้างนาฬิกาเองได้

ตรงนี้เป็นจุดที่ผมคิดว่าโปรเจคเรา *ขัดกับตัวเอง* อยู่

เราบอกว่า **"ชนิดของนาฬิกาคือผลรวมของชิ้นส่วน"** ซึ่งจริง
แต่พอจะสร้างนาฬิกาแบบใหม่จริง ๆ ยังต้องเขียนเมธอด C# ยาว 90 บรรทัด
แปลว่าเครื่องมือของเราไม่ยอมให้เขียน "ผลรวม" นั้นออกมาเป็นข้อมูล — ต้องเขียนเป็นโค้ดเท่านั้น

ทางแก้คือทำไฟล์ข้อมูลชนิดใหม่ขึ้นมา

```
  CuckooClock.asset          ClockBuilder            CuckooClock.prefab
  ┌──────────────────┐       ┌────────────┐          ┌───────────────┐
  │ ตู้      CuckooCase │ อ่าน  │            │  ประกอบ  │ นาฬิกาพร้อมใช้  │
  │ จอ      ClockDial  │ ────► │ เขียนครั้ง  │ ──────► │ ลากลงฉากได้เลย │
  │ ชิ้นส่วน  ลาน+ลูกตุ้ม │       │ เดียว      │          │               │
  │ พลังงาน  โซ่ตุ้มถ่วง  │       │ ไม่แก้อีก   │          │               │
  │ อาการ    Running    │       └────────────┘          └───────────────┘
  └──────────────────┘
     ▲
     ดีไซเนอร์แก้ตรงนี้                ไม่มีใครต้องแตะ
```

**"นาฬิกาแบบใหม่" เข้าระบบทางไฟล์ข้อมูล ไม่ใช่ทางเมธอดใหม่**
นี่คือประโยคที่เราใช้อ้างตลอด เขียนออกมาเป็นเครื่องมือจริง ๆ

### จุดที่ผมตัดสินใจไว้ และอยากให้คุณค้านถ้าไม่เห็นด้วย

ผมเสนอให้ไฟล์ข้อมูลนี้คุมแค่ **การประกอบ** — ว่าใช้ชิ้นส่วนอะไรบ้าง
ส่วน **รูปทรง** ของตู้ยังเป็นโค้ดใน builder เหมือนเดิม

เพราะถ้าดันให้ไฟล์ข้อมูลคุมรูปทรงด้วย มันจะค่อย ๆ กลายเป็นภาษาโปรแกรม
ที่เขียนอยู่ในไฟล์ข้อมูล ซึ่งอ่านยากกว่าและแก้ยากกว่า C# ธรรมดา

## สามอย่างที่อยากให้ตัดสิน

**1 · `IActor` ควรมีแค่สามเมธอดไหม**

ผมเอนไปทางสามเมธอด เพราะเพิ่มทีหลังง่ายกว่าถอดออก
แต่ถ้าคุณรู้อยู่แล้วว่าจะมีของที่ต้องรู้ตำแหน่งผู้เล่น
(เช่นประตูที่ปิดเองเมื่อเดินห่าง หรือไฟที่หรี่ลงตามระยะ)
ควรใส่ `Position` ตั้งแต่แรก เพราะเพิ่มทีหลังต้องแก้ทุกคลาสที่เกี่ยวข้อง

**2 · จะทำถึงข้อไหน**

ข้อ 1–3 กับข้อ 1–5 ตอบคำถามคนละคำถาม แล้วแต่ว่าอยากได้อันไหนก่อน

**3 · ทำบนโปรเจคปัจจุบันเลย หรือค่อย ๆ ทีละโมดูล**

ข้อ 1–2 แตะเกือบทุกไฟล์ ถ้าอยากให้เกมยังเล่นได้ตลอดระหว่างทาง
ผมแนะนำให้เริ่มจาก `Items` กับ `Interaction` ก่อน เพราะเสี่ยงน้อยสุด
แล้วค่อยไล่ขึ้นไป
