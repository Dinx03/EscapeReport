# 3. บทสรุป (ภาษาไทย)

**แบบฟอร์มกำหนดให้มี 2 ย่อหน้าเท่านั้น**
ย่อหน้าแรก = สาเหตุของปัญหา + วิธีดำเนินงาน + การวิเคราะห์
ย่อหน้าที่สอง = ผลที่ได้รับ + ประโยชน์ + ข้อเสนอแนะ

**และกำหนดว่าไม่เกิน 1 หน้า** ซึ่งวัดแล้วว่าเป็นเพดานที่คับ — ส่วนหัวเจ็ดบรรทัด
กับชื่อหัวข้อกินไปเก้าบรรทัด เหลือให้เนื้อความประมาณ **21 บรรทัด หรือราว 1,550 ตัวอักษร**
ร่างฉบับแรกยาว 2,168 ตัวอักษร จึงล้นไปหน้าที่สองแปดบรรทัด ฉบับใช้งานด้านล่างย่อลงให้พอดี
โดยคงตัวเลขที่วัดได้ไว้ทุกตัว

### ร่าง (ฉบับใช้งาน — วัดแล้วพอดีหนึ่งหน้า)

> โครงงานนี้เป็นโจทย์จากพนักงานที่ปรึกษา มีจุดประสงค์ให้ฝึกพัฒนาเกมสามมิติเพื่อเรียนรู้กระบวนการพัฒนาเกม โดยกำหนดให้เป็นเกมแนวห้องหลบหนี กำหนดปุ่มควบคุมและเงื่อนไขของเกมมาให้ และให้ปริศนาเป็นงานออกแบบของผู้เขียนเอง เพื่อให้ได้ผ่านกระบวนการพัฒนาเกมครบทุกขั้น ตั้งแต่ออกแบบเนื้อหาจนถึงเขียนโปรแกรมและทดสอบ
>
> ผู้เขียนตั้งใจออกแบบซอฟต์แวร์ของเกมให้เป็นมอดูลาร์ตั้งแต่เริ่ม คือให้วัตถุแต่ละชิ้นเกิดจากการประกอบคอมโพเนนต์ย่อยที่ทำหน้าที่อย่างเดียว แทนการเขียนคลาสใหม่ต่อวัตถุหนึ่งชนิด เพื่อให้เพิ่มวัตถุใหม่ได้โดยไม่แก้โปรแกรมที่เขียนไว้แล้ว ด้วยเจตนานี้จึงเลือกให้ปริศนาห้าองก์มีนาฬิกาเป็นแกน เพราะนาฬิกาใช้ส่วนประกอบร่วมกัน คือหน้าปัดกับกลไก แต่พฤติกรรมต่างกันได้มาก ทั้งเดินตรง เดินช้า หยุดเดิน และตีบอกเวลา จึงทำให้ผลของการออกแบบแบบมอดูลาร์เห็นได้ชัด
>
> ผลที่ได้คือเกมที่เล่นจบได้ มีห้าห้องเรียงเป็นเส้นทางเดียว ห้องละปริศนา และมีนาฬิกา 46 เรือนที่สร้างจากหน้าปัดและกลไกชุดเดียวกัน ต่างกันเฉพาะชิ้นส่วนที่ประกอบเข้าไป เช่น ลานสปริง ลูกตุ้ม หรือกลไกตีบอกเวลา การเพิ่มนาฬิกาหรือวัตถุปริศนาชนิดใหม่จึงทำได้ด้วยการเลือกชิ้นส่วนมาประกอบ ไม่ต้องเขียนโปรแกรมเพิ่ม และมีนาฬิกาหนึ่งเรือนที่ประกอบจากไฟล์ข้อมูลไฟล์เดียวโดยไม่มีโปรแกรมรองรับ โครงสร้างนี้ยืนยันด้วยชุดทดสอบอัตโนมัติ 15 กรณี ข้อเสนอแนะคือขยายชุดทดสอบให้ครอบคลุมโมดูลปริศนา

### ร่างฉบับยาว — เก็บไว้อ้างอิง ใช้ไม่ได้เพราะเกินหนึ่งหน้า

เนื้อหาเหมือนฉบับใช้งาน แต่มีประโยคขยายเพิ่ม เช่น เงื่อนไขสองข้อของโจทย์
วิธีวิเคราะห์สามแบบ และรายละเอียดว่าชุดทดสอบยังไม่ครอบส่วนผู้เล่นและส่วนติดต่อผู้ใช้
ถ้าอาจารย์ที่ปรึกษาอนุญาตให้บทสรุปยาวเกินหนึ่งหน้า ให้ใช้ฉบับนี้แทน

> โครงงานนี้มีที่มาจากโจทย์ที่ได้รับมอบหมายจากพนักงานที่ปรึกษา ให้พัฒนาเกมจำลอง
> ห้องหลบหนีมุมมองบุคคลที่หนึ่งบนเอนจิน Unity โดยกำหนดปุ่มควบคุมและธีมของเกมมาให้
> ส่วนปริศนาและการจัดวางฉากเป็นงานออกแบบของผู้เขียนเอง ภายในระยะเวลาที่จำกัด
> เงื่อนไขสองข้อนี้ทำให้ปัญหาที่แท้จริงของโครงงานไม่ใช่การเขียนโปรแกรมให้เกมทำงานได้
> แต่เป็นการออกแบบโครงสร้างซอฟต์แวร์ให้การเพิ่มวัตถุชนิดใหม่หรือการเปลี่ยนกฎของปริศนา
> ไม่บังคับให้ต้องแก้ไขโปรแกรมส่วนที่เขียนไว้แล้ว ผู้เขียนจึงเลือกออกแบบระบบวัตถุโต้ตอบ
> ทั้งหมดด้วยการประกอบคอมโพเนนต์ย่อยเข้าด้วยกันแทนการสืบทอดคลาส และให้คอมโพเนนต์
> ค้นหาผู้ร่วมงานผ่านส่วนต่อประสาน (interface) ตามบทบาท แทนการอ้างอิงถึงคลาสที่เจาะจง
> จากนั้นได้บังคับขอบเขตของโมดูลด้วยไฟล์ Assembly Definition เพื่อให้การพึ่งพาที่ผิดทิศ
> กลายเป็นข้อผิดพลาดตอนคอมไพล์ และเขียนชุดทดสอบเพื่อยืนยันว่าข้อกำหนดของ
> สถาปัตยกรรมยังเป็นจริงอยู่ การวิเคราะห์ในรายงานอาศัยการวัดจากไฟล์ของโครงงานโดยตรง
> ทั้งจำนวนบรรทัด ความสัมพันธ์การพึ่งพาระหว่างโมดูล และการทดลองในเชิงตัวเลข
>
> ผลการดำเนินงานได้เกมที่เล่นได้ครบห้าห้องและปริศนาห้าองก์ตามเส้นทางเดียว โดยโปรแกรม
> มีขนาด 78 ไฟล์ 10,604 บรรทัด (นับบรรทัดที่ไม่ว่าง) ประกอบด้วยคลาส MonoBehaviour
> 51 คลาสที่สืบทอดจาก MonoBehaviour โดยตรงทั้งหมดและไม่มีการสืบทอดระหว่างกันเลย
> ส่วนต่อประสาน 12 รายการ และการนำไปสร้างจริง 29 ความสัมพันธ์ ขอบเขตของโมดูลถูกบังคับ
> ด้วยไฟล์ Assembly Definition 6 ไฟล์ และมีชุดทดสอบ 15 กรณีที่ทำงานได้โดยไม่ต้องเปิดฉาก
> และไม่ต้องมีตัวผู้เล่น ประโยชน์ที่วัดได้ชัดที่สุดคือนาฬิกาทั้ง 46 เรือนในเกมใช้หน้าปัดเดียวกัน
> และนาฬิกาแต่ละชนิดเกิดจากการเลือกคอมโพเนนต์ที่ประกอบเข้าไป ไม่ใช่การเขียนคลาสใหม่
> จึงเปลี่ยนกลไกของปริศนาระหว่างการพัฒนาได้โดยไม่ต้องแก้โปรแกรมส่วนอื่น ข้อจำกัดที่พบ
> คือชุดทดสอบครอบคลุมเฉพาะโมดูลชั้นล่างสี่โมดูล ยังไม่ครอบคลุมส่วนผู้เล่นและส่วนติดต่อ
> ผู้ใช้ มีข้อความภาษาไทย 17 บรรทัดที่ยังฝังอยู่ในโปรแกรมและต้องแก้โปรแกรมหากจะแปลภาษา
> และพบข้อบกพร่องที่ยังไม่ได้แก้หนึ่งรายการซึ่งเกิดจากลำดับการเรียกเมธอด Awake ที่เอนจิน
> ไม่รับประกัน ข้อเสนอแนะสำหรับการพัฒนาต่อคือการขยายชุดทดสอบให้ครอบคลุมโมดูลปริศนา
> การย้ายข้อความทั้งหมดออกไปเป็นไฟล์ข้อมูล และการกำหนดข้อตกลงเรื่องช่วงเวลาที่เรียกใช้
> ส่วนต่อประสานได้ให้ชัดเจน เนื่องจากส่วนต่อประสานบังคับได้เพียงลายเซ็นของเมธอด
> แต่บังคับช่วงเวลาที่เรียกใช้ไม่ได้

# 4. Summary (ภาษาอังกฤษ)

**สองย่อหน้าเท่ากัน เนื้อหาตรงกับบทสรุปภาษาไทย**

**ไม่เกิน 1 หน้าเช่นกัน** ร่างฉบับแรกยาว 2,775 ตัวอักษร ล้นไปหน้าที่สองสิบห้าบรรทัด
ฉบับใช้งานด้านล่างย่อลงเหลือราว 1,500 ตัวอักษร โดยคงตัวเลขทุกตัวให้ตรงกับบทสรุปภาษาไทย

### ร่าง (ฉบับใช้งาน — วัดแล้วพอดีหนึ่งหน้า)

> This project was an assignment from the author's workplace supervisor, whose purpose was to practise building a 3D game and learn the game development process. It specified an escape room game and fixed the controls and conditions, while the puzzles were left to the author, so that the author would go through every stage of development, from designing content to writing and testing code.
>
> The author intended the game's software to be modular from the start: each object is assembled from small components that each do one job, rather than written as a new class per kind of object, so a new kind of object can be added without editing existing code. That intent is why clocks were chosen as the core of all five puzzle acts: clocks plainly share their parts, a dial and a movement, yet behave very differently — keeping time, running slow, standing still, striking the hour — which makes a modular design easy to see.
>
> The result is a game that can be played through once, with five rooms in a single route and one puzzle in each, and 46 clocks in the house, every one built from the same dial and movement, differing only in the parts attached, such as a mainspring, a pendulum or a striking mechanism. Adding a new clock or puzzle object is therefore a matter of choosing parts, with no further code, and one clock is assembled from a single data file with no code behind it. The structure is checked by 15 automated tests, and the recommendation is to extend them to the puzzle module.

### ร่างฉบับยาว — เก็บไว้อ้างอิง ใช้ไม่ได้เพราะเกินหนึ่งหน้า

> This project originated from an assignment given by the author's workplace supervisor:
> to develop a first-person escape room simulator using the Unity engine. The supervisor
> specified the control scheme and the genre, while the puzzles and the level dressing were
> left to the author to design, within a limited schedule. These two conditions meant that
> the real engineering problem was not making the game run, but designing a software
> structure in which adding a new kind of interactive object, or changing the rule of a
> puzzle, would not force edits to code that had already been written. The author therefore
> built every interactive object by composing small components rather than by subclassing,
> and had those components discover their collaborators through role-named interfaces
> instead of referring to concrete classes. Module boundaries were then enforced with
> Assembly Definition files, so that a dependency pointing the wrong way becomes a compile
> error rather than a matter of discipline, and a test suite was written to assert that the
> architectural constraints still hold. The analysis presented in this report is based on
> direct measurement of the project's own files: line counts, the dependency relations
> between modules, and numerical experiments on the timing code.
>
> The result is a playable game of five rooms and five puzzle acts along a single route.
> The program comprises 78 source files totalling 10,604 non-blank lines, made up of
> 51 MonoBehaviour classes — every one of which derives directly from MonoBehaviour, with
> no inheritance between them — together with 12 interfaces and 29 implementing
> relationships. Module boundaries are enforced by 6 Assembly Definition files, and the
> suite of 15 test cases runs without loading a scene and without a player object. The
> clearest measurable benefit is that all 46 clocks in the game share a single dial
> implementation, and that the kind of each clock is determined by which components are
> attached to it rather than by a dedicated class, which allowed the mechanism of a puzzle
> to be replaced mid-development without altering any other part of the program.
> The limitations found are that the test suite covers only the four lower modules and not
> the player or user-interface code, that 17 lines of Thai text remain embedded in the
> program and would require code changes in order to be translated, and that one unresolved
> defect remains, caused by an Awake call order that the engine does not guarantee.
> The recommendations for further work are to extend the test suite to the puzzle module,
> to move all in-game text out into data files, and to state explicitly when each interface
> may be called, since an interface can enforce a method signature but cannot enforce the
> time at which that method is invoked.

⚠️ **ตรวจก่อนใช้** ชื่อ Summary ต้องเป็นชื่อโครงงานภาษาอังกฤษที่เลือกไว้
และถ้าแก้ตัวเลขใดในบทสรุปภาษาไทย **ต้องแก้ที่นี่ให้ตรงกันทุกตัว**
